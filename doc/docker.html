01

Bắt đầu & lộ trình học

Bạn sẽ học được gì và nên đi theo thứ tự nào?

Docker giúp đóng gói ứng dụng cùng những thứ nó cần để chạy thành container, tạo trải nghiệm nhất quán hơn giữa máy cá nhân, môi trường kiểm thử và máy chủ.

🧱

Nền tảng

Hiểu image, container, daemon, network; chạy và quan sát container.

🛠️

Thực hành

Viết Dockerfile, chạy Flask, ghép Redis bằng Compose, giữ dữ liệu bằng volume.

🔐

Vận hành

Xử lý lỗi, quản lý tài nguyên, chọn base image và nâng mức an toàn.

Điều kiện cần

  • Máy Windows, macOS hoặc Linux có thể cài Docker; có quyền cài phần mềm.
  • Biết tạo thư mục, lưu tệp văn bản và chạy lệnh trong terminal.
  • Không bắt buộc biết Python, vì bài lab đã cung cấp toàn bộ mã nguồn.
🧭 Cách sử dụng tài liệu

Đọc từ chương 01 đến 09 để làm được dự án hoàn chỉnh; dùng các chương 10–17 như sổ tay tra cứu. Mỗi khối lệnh đều có nút Sao chép. Trên desktop có mục lục và tìm kiếm nhanh ở bên trái.

Docker phù hợp khi nào?

Phù hợp khi bạn muốn cài một dịch vụ chỉ bằng một lệnh, chạy nhiều bản ứng dụng tách biệt, thống nhất môi trường nhóm, đóng gói ứng dụng cho CI/CD hoặc triển khai dịch vụ. Docker không thay thế kiến thức cấu hình, sao lưu, giám sát hay bảo mật.

02

Docker hoạt động như thế nào?

Image → container → cổng mạng → dữ liệu

Hãy hình dung image là bản thiết kế đóng gói, còn container là tiến trình được khởi chạy từ bản thiết kế ấy. Bạn có thể tạo nhiều container từ một image và mỗi container có vòng đời, lớp ghi và cấu hình chạy riêng.

Thành phầnÝ nghĩaVí dụ
Docker CLICông cụ gửi lệnh đến Docker Enginedocker ps
Docker daemon / EngineDịch vụ quản lý image, container, mạng và volumedockerd
DockerfileTệp khai báo cách build imageFROM python:3.13-slim
ImageMẫu read-only theo layer, dùng tạo containernginx:alpine
ContainerĐối tượng chạy từ image, có lớp ghi riêngmy-nginx
RegistryNơi lưu và phân phối imageDocker Hub
ComposeKhai báo nhiều dịch vụ trong tệp YAMLcompose.yaml

Container khác máy ảo (VM) ra sao?

Container

Các container Linux dùng chung kernel của môi trường Linux host/VM chạy Docker Engine, nên thường nhẹ và khởi động nhanh hơn. Cách ly dựa trên namespaces, cgroups và cơ chế bảo vệ khác.

Máy ảo (VM)

Mỗi VM có hệ điều hành khách và kernel riêng trên hypervisor. Thường phù hợp khi cần cách ly ở cấp hệ điều hành hoặc chạy kernel khác.

Điểm dễ nhầm

Trên Windows và macOS, Docker Desktop thường dùng một VM/động cơ ảo hóa để vận hành Linux containers. Container không phải VM độc lập. Container cũng không tự động an toàn ngang VM trong mọi tình huống.

Vòng đời cơ bản

docker run tạo và chạy một container mới. docker start chạy lại container đã tạo. docker stop yêu cầu tiến trình dừng; docker rm xóa container. Image vẫn còn khi container bị xóa.

03

Cài đặt Docker

Chọn hệ điều hành và kiểm tra cấu hình

Trên máy cá nhân, Docker Desktop là lựa chọn dễ bắt đầu. Trên máy chủ Linux không có giao diện đồ họa, thường cài Docker Engine và Compose plugin. Chọn tab tương ứng:

  1. Kiểm tra WSL 2 và ảo hóaMở PowerShell, kiểm tra bản WSL bằng wsl --version; nếu chưa cài, có thể dùng wsl --install trong terminal với quyền cần thiết rồi khởi động lại theo hướng dẫn của Windows.
  2. Cài Docker DesktopTải từ trang cài đặt Docker Desktop cho Windows. Chọn backend phù hợp, thông thường là WSL 2, và khởi động Docker Desktop.
  3. Xác nhận Docker Engine đã chạyMở PowerShell/Windows Terminal và thực hiện các lệnh kiểm tra chung bên dưới.
Gợi ý

Đặt mã nguồn trong filesystem của bản phân phối Linux WSL khi phát triển bằng công cụ Linux để có trải nghiệm I/O tốt hơn. Các yêu cầu phiên bản Windows, WSL và chính sách cấp phép có thể thay đổi; kiểm tra trang Docker Docs chính thức.

  1. Chọn bản phù hợpKiểm tra máy dùng Apple silicon hay Intel rồi truy cập Docker Desktop cho Mac.
  2. Cài ứng dụngLàm theo hướng dẫn cài đặt, mở Docker Desktop và chấp thuận các quyền cần thiết.
  3. Thử trong TerminalChạy các lệnh kiểm tra bên dưới.
Lưu ý

Ảnh image có kiến trúc CPU khác có thể chạy qua mô phỏng, nhưng tốc độ và khả năng tương thích có thể khác. Ưu tiên image hỗ trợ arm64 trên Apple silicon.

Các lệnh dưới đây áp dụng cho Ubuntu được Docker hỗ trợ, thiết lập kho APT chính thức. Trước tiên đọc hướng dẫn Ubuntu mới nhất để kiểm tra gói xung đột và phiên bản hệ điều hành. Nếu đã có Docker cũ, làm theo mục gỡ các gói xung đột trong tài liệu trước khi cài.

Terminal Ubuntu · thêm kho Docker
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

Kiểm tra dịch vụ bằng sudo systemctl status docker. Nếu Docker chưa chạy, dùng sudo systemctl start docker. Theo mặc định trên Linux có thể cần sudo trước lệnh Docker.

Quyền truy cập Docker là quyền mạnh

Thêm người dùng vào nhóm docker gần như trao quyền root trên máy đó. Chỉ làm khi hiểu hệ quả; xem Linux post-installation hoặc cân nhắc rootless mode.

Kiểm tra cài đặt

Terminal · Windows / macOS / Linux
docker --version
docker version
docker compose version
docker run --rm hello-world

Nếu thấy thông báo “Hello from Docker!”, bạn đã chạy container đầu tiên thành công. Trên Linux, nếu lỗi quyền, chạy lại với sudo docker ... sau khi xác nhận daemon hoạt động.

04

Chạy container đầu tiên

Bắt đầu bằng Nginx, không cần viết ứng dụng

1. Khởi chạy web server

Terminal · chạy Nginx nền
docker run -d --name web-demo -p 8080:80 nginx:alpine

Truy cập http://localhost:8080. Nếu thấy trang chào của Nginx, container đang hoạt động. Đây là ví dụ phát triển cục bộ, không nên mặc định công khai dịch vụ lên Internet.

Phần của lệnhCó tác dụng gì?
runTạo container mới từ image rồi chạy.
-dChạy nền (detached).
--name web-demoĐặt tên dễ nhớ.
-p 8080:80Chuyển tiếp cổng 8080 ở máy host đến cổng 80 trong container.
nginx:alpineImage và tag sẽ sử dụng; Docker tải image nếu chưa có.
⚠️ Chú ý về -p

-p 8080:80 thường bind trên tất cả địa chỉ mạng của host. Nếu chỉ muốn truy cập từ máy đang dùng, ưu tiên -p 127.0.0.1:8080:80.

2. Quan sát rồi dọn dẹp

Terminal · quan sát Nginx
docker ps
docker logs web-demo
docker exec web-demo nginx -v
docker stop web-demo
docker rm web-demo

exec chạy lệnh mới bên trong container đang chạy; không khởi tạo container khác. logs đọc log tiến trình chính của container.

05

Quản lý container mỗi ngày

Chạy, dừng, xem log, vào shell và quan sát tài nguyên
LệnhÝ nghĩa
docker psLiệt kê container đang chạy.
docker ps -aLiệt kê cả container đã dừng.
docker stop NAMEGửi tín hiệu dừng tiến trình chính.
docker start NAMEKhởi động lại container đã tạo.
docker restart NAMEKhởi động lại container.
docker rm NAMEXóa container đã dừng.

Foreground, background và terminal

-d chạy nền, -i giữ STDIN mở, -t cấp terminal giả. Kết hợp -it rất phổ biến để mở shell. Các image tối giản có thể không có Bash; khi đó thử sh.

Terminal · thử shell tương tác
docker run --rm -it alpine:3.21 sh
# Bên trong container:
cat /etc/os-release
exit

--rm tự xóa container khi tiến trình kết thúc; phù hợp với tác vụ thử nghiệm hoặc lệnh chạy một lần.

Phân biệt

docker run mỗi lần tạo container mới; docker start dùng lại container đã tồn tại. Nếu thấy nhiều bản “Exited”, thường do bạn gọi run lặp lại.

06

Image, layer, tag & registry

Hiểu chính xác Docker tải và lưu những gì

Một image là tập hợp layer có thể chia sẻ và cache. Tag như nginx:alpine là nhãn tham chiếu, không đảm bảo nội dung bất biến theo thời gian. Để cố định chính xác image, có thể tham chiếu bằng digest @sha256:....

Terminal · làm việc với image
docker pull nginx:alpine
docker image ls
docker image inspect nginx:alpine
docker history nginx:alpine
docker tag nginx:alpine local-nginx:demo
docker image ls local-nginx
docker rmi local-nginx:demo

Thông thường image có tên dạng [registry/][namespace/]repository:tag, ví dụ docker.io/library/nginx:alpine. Nếu không ghi registry, Docker dùng quy tắc mặc định. Docker Hub là một registry phổ biến, không phải registry duy nhất.

Tag latest thực sự có nghĩa gì?

latest chỉ là tên tag mặc định trong nhiều tình huống, không tự đảm bảo phiên bản phần mềm mới hoặc an toàn nhất. Với dự án quan trọng, nên chọn phiên bản cụ thể, kiểm thử và có chiến lược cập nhật.

Mẹo build

Layer được cache giúp build lại nhanh. Khi một lớp thay đổi, các lớp phụ thuộc phía sau thường cần được tạo lại. Đó là lý do tách COPY requirements.txt và bước cài dependency khỏi COPY mã nguồn.

07

Dockerfile chi tiết

Viết công thức để tạo image của chính bạn

Một Dockerfile mô tả image cần build: chọn nền tảng, cài dependency, sao chép mã nguồn, thiết lập quyền và chọn tiến trình khởi chạy.

Chỉ thịCông dụngLưu ý
FROMChọn base image / build stageNên chọn nguồn đáng tin cậy.
WORKDIRĐặt thư mục làm việcTác động đến lệnh phía sau.
COPYChép tệp từ build contextTôn trọng .dockerignore.
RUNThực hiện khi build imageVí dụ cài package.
ENVĐặt biến môi trường trong imageKhông nhúng mật khẩu.
ARGTham số dành cho quá trình buildKhông dùng để bảo vệ secret.
EXPOSEGhi nhận cổng ứng dụng dự kiến dùngKhông tự mở cổng host.
USERChọn user chạy lệnh/ứng dụngƯu tiên non-root.
CMDLệnh mặc định khi container chạyCó thể ghi đè khi chạy.
ENTRYPOINTĐặt executable chínhKết hợp với CMD khi cần.

Ví dụ Dockerfile cực nhỏ

Dockerfile · chỉ để minh họa
FROM alpine:3.21
WORKDIR /app
COPY message.txt .
CMD ["cat", "message.txt"]

Tạo thêm tệp message.txt chứa văn bản bất kỳ. Sau đó:

Terminal · build / chạy
docker build -t my-message:1.0 .
docker run --rm my-message:1.0

Dấu . cuối lệnh là build context (thư mục có các tệp bạn cho Docker build sử dụng). Đây không phải dấu kết thúc lệnh tùy ý. Docker sẽ tìm tệp Dockerfile mặc định trong context.

CMD dạng JSON exec form

Ưu tiên cú pháp CMD ["executable", "arg1"] thay cho shell form khi thích hợp, giúp việc xử lý tín hiệu và tiến trình chính rõ ràng hơn.

08

Lab: đóng gói ứng dụng Flask

Tự tay viết mã, build image và chạy HTTP API
Hands-on lab · phần 1 / 2

Ta sẽ tạo API Python nhỏ, chạy được độc lập ở chương này. Sang chương 09, ta kết nối thêm Redis để đếm lượt truy cập mà không phải sửa Dockerfile.

Bước 1 — Tạo cấu trúc dự án

Tạo thư mục docker-flask-demo bằng File Explorer / Finder / terminal, sau đó tạo đúng bốn tệp sau bằng VS Code hoặc trình soạn thảo văn bản thuần:

docker-flask-demo/ ├── app.py ├── requirements.txt ├── Dockerfile └── .dockerignore

Bước 2 — Viết mã ứng dụng

app.py
import os
from flask import Flask, jsonify
import redis

app = Flask(__name__)
app.json.ensure_ascii = False

@app.get("/")
def index():
    host = os.getenv("REDIS_HOST")
    if not host:
        return jsonify(message="Xin chào Docker!", mode="standalone")

    try:
        db = redis.Redis(
            host=host,
            port=int(os.getenv("REDIS_PORT", "6379")),
            decode_responses=True,
            socket_connect_timeout=2,
        )
        visits = db.incr("visits")
    except redis.RedisError:
        return jsonify(error="Không kết nối được Redis"), 503

    return jsonify(message="Xin chào Docker!", visits=visits, mode="compose")

@app.get("/health")
def health():
    return jsonify(status="ok")

Chương trình kiểm tra biến REDIS_HOST: không có thì chạy chế độ một service; nếu có thì kết nối Redis và tăng bộ đếm. Route /health dùng để kiểm tra HTTP server còn hoạt động (không xác nhận Redis khỏe).

requirements.txt
Flask==3.1.1
redis==6.2.0
gunicorn==23.0.0

Ví dụ dùng dependency được ghim phiên bản để dễ tái hiện; khi làm dự án thật, hãy cập nhật các phiên bản đã kiểm thử và vá bảo mật.

Bước 3 — Tạo Dockerfile

Dockerfile
FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .

RUN useradd --create-home --uid 10001 appuser
USER appuser

EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]

gunicorn là WSGI server phù hợp hơn Flask development server cho ví dụ chạy service. User không phải root giảm tác động của một số lỗi ứng dụng. Ở mức production cần xem thêm timeout, worker, logging, health check và giám sát.

.dockerignore
.git/
.venv/
__pycache__/
*.pyc
.env
.env.*
.DS_Store
README.local.md

.dockerignore giúp tránh gửi tệp dư thừa và một số tệp nhạy cảm vào build context. Nó không thay thế quy trình quản lý secret đúng cách.

Bước 4 — Build và chạy image

Mở terminal tại thư mục docker-flask-demo — tức thư mục chứa Dockerfile:

Terminal · trong docker-flask-demo/
docker build -t flask-counter:1.0 .
docker run -d --name flask-standalone \
  -p 127.0.0.1:8000:8000 flask-counter:1.0
docker logs flask-standalone
Windows PowerShell

Phần lệnh docker run phía trên dùng ký tự tiếp dòng \ của Bash. Trong PowerShell, dùng một dòng sau thay thế:

PowerShell · lệnh tương đương
docker run -d --name flask-standalone -p 127.0.0.1:8000:8000 flask-counter:1.0

Vào http://localhost:8000 (hoặc dùng lệnh bên dưới). Kết quả dự kiến:

HTTP response · minh họa
{"message":"Xin chào Docker!","mode":"standalone"}
Terminal · kiểm tra và giải phóng cổng
docker ps

docker rm flask-standalone
✅ Kết quả cần đạt

Bạn đã tạo image từ mã nguồn, chạy ứng dụng dưới user không phải root, truy cập được HTTP API từ host và biết cách xóa container khi đã xong.

09

Docker Compose + Redis

Khởi chạy nhiều container bằng một cấu hình
Hands-on lab · phần 2 / 2

Thay vì chạy từng container rồi tự tạo mạng, Docker Compose mô tả toàn bộ ứng dụng bằng YAML: service, network, volume, biến môi trường, điều kiện khởi động và cổng. Cú pháp hiện đại là docker compose (có dấu cách).

Bước 1 — Thêm compose.yaml

Trong thư mục docker-flask-demo ở chương 08, tạo thêm tệp compose.yaml dưới đây. Giữ nguyên các tệp còn lại.

compose.yaml
name: docker-flask-redis

services:
  web:
    build: .
    image: flask-counter:1.0
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      REDIS_HOST: redis
      REDIS_PORT: "6379"
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  redis_data:

Volumes & bind mounts

Cách giữ dữ liệu khi container bị tạo lại

Lớp ghi của container tồn tại cùng container. Khi xóa container, dữ liệu chỉ nằm trong lớp ghi đó thường mất theo. Dữ liệu cần tồn tại lâu như database, ảnh người dùng hay tệp upload nên đặt ngoài lớp ghi qua mount.

Kiểu lưu trữĐặc điểmDùng khi nào?
Named volumeDocker quản lý vị trí và vòng đờiDatabase, dữ liệu ứng dụng cần bền vững.
Bind mountÁnh xạ đường dẫn thực ở máy hostChỉnh source code, chia sẻ tệp cấu hình.
tmpfsLưu trong vùng nhớ tạm (trên Linux)Dữ liệu tạm, không muốn ghi xuống đĩa.
Writable layerGắn với container và mất khi xóaThay đổi tạm, không cần giữ lại.

Thử nghiệm named volume trong 60 giây

Terminal · dữ liệu sống lâu hơn container
docker volume create demo-data

docker run --rm -v demo-data:/data alpine:3.21 \
  sh -c 'echo xin-chao > /data/note.txt'

docker run --rm -v demo-data:/data:ro alpine:3.21 \
  cat /data/note.txt

docker volume inspect demo-data
docker volume rm demo-data

Các lệnh trên dùng cú pháp tiếp dòng của Bash. Trong PowerShell, nhập mỗi docker run ... trên một dòng và dùng dấu nháy kép quanh phần sh -c nếu cần. Kết quả đọc phải là xin-chao dù container đầu tiên đã tự xóa.

Bind mount trong Compose

compose.yaml · ví dụ riêng cho phát triển
services:
  app:
    build: .
    volumes:
      - ./src:/app/src:ro  # Chỉ đọc mã nguồn từ host

Đây là ví dụ minh họa cú pháp bind mount cho một dự án có thư mục src, không phải phần thêm trực tiếp vào lab Flask ở chương 08. Đường dẫn tương đối trong Compose được tính theo vị trí tệp Compose (với trường hợp Compose thông thường).

Sao lưu trước khi xóa

docker volume prune và docker compose down -v có thể xóa dữ liệu bạn cần. Đừng nhầm volume với cơ chế backup: volume chỉ là nơi lưu dữ liệu, không tự tạo bản sao an toàn.

Networking & ports

Container nói chuyện với nhau bằng cách nào?

Docker cung cấp cơ chế mạng cho container. Với user-defined bridge network và network mặc định do Compose tạo, các container/service thường tìm nhau qua tên, nhờ DNS nội bộ của Docker.

Ba địa chỉ cần phân biệt

  • localhost bên trong container là chính container đó, không phải máy host hay container khác.
  • redis:6379 là địa chỉ Redis mà service web dùng trên network Compose.
  • 127.0.0.1:8000:8000 trong ports publish cổng container ra loopback của host, giảm việc vô tình mở ra mạng ngoài.

Tạo mạng riêng không cần Compose

Terminal · 2 container cùng network
docker network create lab-net
docker run -d --name redis-net --network lab-net redis:7-alpine
docker run --rm --network lab-net redis:7-alpine \
  redis-cli -h redis-net ping
# Kết quả kỳ vọng: PONG

docker rm -f redis-net
docker network rm lab-net

Bạn có thể liệt kê mạng bằng docker network ls và xem chi tiết bằng docker network inspect lab-net. Trong Compose, không cần viết network thủ công cho hầu hết mô hình đơn giản.

EXPOSE khác ports

EXPOSE 8000 trong Dockerfile là metadata mô tả cổng dự kiến. Nó không thay thế -p hay mục ports, và cũng không phải một lớp kiểm soát truy cập.

Environment & secrets

Đưa cấu hình vào container mà không hard-code

Cùng một image có thể chạy ở nhiều môi trường bằng cách truyền cấu hình lúc khởi chạy: URL API, cổng, chế độ log, hostname database... Điều này làm image tái sử dụng được và giảm nhu cầu rebuild chỉ để đổi cấu hình.

Biến môi trường

Terminal · ví dụ biến môi trường
docker run --rm -e APP_MODE=development alpine:3.21 \
  sh -c 'echo "$APP_MODE"'

.env và env_file trong Compose

Compose thường tự đọc tệp .env để thay thế biến trong cấu hình. Nếu bạn muốn cấp một tệp biến môi trường trực tiếp cho container, dùng env_file:

compose.yaml · ví dụ cú pháp
services:
  web:
    image: example/web:1.0
    env_file:
      - ./app.env
    ports:
      - "127.0.0.1:${APP_PORT:-8000}:8000"

Ở đây, app.env được truyền vào container; ${APP_PORT:-8000} được Compose thay thế từ môi trường hoặc tệp .env (với giá trị mặc định là 8000). Hai cơ chế có mục đích khác nhau.

Không đưa mật khẩu trực tiếp vào image

Biến môi trường thuận tiện nhưng không phù hợp cho mọi secret: giá trị có thể bị lộ qua cách cấu hình, lệnh kiểm tra, log hoặc người có quyền Docker. Hãy dùng cơ chế secrets phù hợp môi trường triển khai hoặc công cụ quản lý bí mật chuyên dụng.

compose.yaml · ví dụ khai báo secret từ file
services:
  app:
    image: example/app:1.0
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt

Với triển khai Compose thông thường, secret này được mount vào container dạng tệp, thường ở /run/secrets/db_password. Ứng dụng cần đọc nội dung tệp đó; không phải image nào cũng tự biết dùng secret. File nguồn vẫn phải được bảo vệ trên host. Ví dụ này không chạy độc lập vì example/app:1.0 chỉ là tên minh họa.

Đừng để lộ credentials

Không commit tệp chứa mật khẩu, private key hay token vào Git. Không đưa secret vào ARG/ENV lúc build rồi cho rằng image đã giấu được chúng. Khi build cần secret, tìm hiểu Build secrets.

13

Bảo mật & vận hành production

Mặc định an toàn hơn, nhưng không có cấu hình thần kỳ

Container cô lập ứng dụng ở mức nhất định, không có nghĩa ứng dụng được bảo mật tự động. Hãy quản trị image, runtime, mạng, secrets và quyền truy cập Docker Engine như những thành phần hệ thống quan trọng.

✅ Nên làm

  • Chọn image chính thức/nguồn tin cậy, cập nhật và quét lỗ hổng.
  • Chạy tiến trình ứng dụng dưới user không phải root khi khả thi.
  • Giới hạn tài nguyên, thu thập log và có health check.
  • Chỉ publish các cổng thật sự cần thiết; phân đoạn mạng.
  • Backup và thử khôi phục dữ liệu định kỳ.

⛔ Cần tránh

  • Dùng --privileged không có lý do rõ ràng.
  • Gắn /var/run/docker.sock vào container lạ.
  • Để mật khẩu trong Dockerfile, image hoặc Git.
  • Xuất database/Redis ra Internet khi không cần.
  • Cho mọi người truy cập Docker daemon tùy ý.

Giới hạn tài nguyên khi chạy

Terminal · ví dụ Nginx có giới hạn
docker run --rm -d --name limited-web \
  --memory 256m --cpus 0.5 \
  -p 127.0.0.1:8081:80 nginx:alpine

docker stats limited-web
docker stop limited-web

--memory giới hạn bộ nhớ; --cpus giới hạn phần CPU có thể dùng. Hãy chọn giá trị theo yêu cầu thực tế và theo dõi trước khi áp dụng cứng cho môi trường tải cao.

Cải thiện cấu hình Compose cho production

compose.yaml · các khóa minh họa để tham khảo
services:
  app:
    image: example/app:1.0
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    mem_limit: 512m
    restart: unless-stopped

Đây là mẫu tham khảo riêng, không phải cấu hình có thể ghép vào mọi ứng dụng. read_only có thể làm app lỗi nếu cần ghi; hãy cấp writable mount cho đúng vị trí. Quyền user, số worker, giới hạn RAM và chính sách restart cần kiểm tra theo dịch vụ cụ thể.

Docker không thay thế triển khai production

Máy chủ thật còn cần TLS, reverse proxy, firewall, cập nhật hệ điều hành, bảo vệ registry, observability, quản lý secret, chiến lược rollback, backup và kiểm thử khôi phục. Với nhiều node hoặc autoscaling, có thể cần hệ thống orchestration khác (ví dụ Kubernetes), không chỉ Compose.

Tối ưu image & build

Image nhỏ hơn, build nhanh hơn, ít rủi ro hơn

1. Sắp xếp các lớp để tận dụng cache

Với dự án Python ở chương 08, ta đã COPY requirements.txt . rồi RUN pip install ..., sau đó mới COPY app.py .. Nhờ vậy thay đổi mã nguồn mà dependency không đổi thường không cần cài lại thư viện.

2. Dùng multi-stage build khi phù hợp

Multi-stage cho phép build bằng image chứa compiler/tool rồi chỉ đưa artifact cần thiết vào image runtime. Ví dụ sau minh họa cho một dự án frontend Node.js đã có package.json, package-lock.json và lệnh build xuất thư mục dist; không áp dụng trực tiếp cho lab Flask.

Dockerfile · frontend Node build → Nginx runtime
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

Image cuối chỉ nhận phần dist từ stage build, không mang theo toàn bộ node_modules hoặc source build. Bạn vẫn cần cấu hình Nginx đúng với routing và yêu cầu của ứng dụng.

3. Những thao tác build thực dụng

Terminal · kiểm soát cache / image
docker build -t flask-counter:1.1 .
docker build --pull -t flask-counter:1.1 .
docker build --no-cache -t flask-counter:1.1 .
docker image ls
docker system df
docker buildx version
  • --pull yêu cầu kiểm tra base image mới hơn; không tự cập nhật mọi dependency trong app.
  • --no-cache bỏ cache của bước build; không đồng nghĩa tự kéo base image mới.
  • --pull --no-cache kết hợp cả hai khi cần kiểm tra lại pipeline, nhưng build sẽ chậm hơn.
  • .dockerignore tránh gửi node_modules, .venv, tệp tạm và thông tin nhạy cảm vào context.
Ưu tiên

Đo kích thước, tốc độ, khả năng bảo trì và tính tương thích trước khi cố giảm image đến mức cực nhỏ. Image tối giản không phải lúc nào cũng phù hợp với native libraries, debug hay môi trường của bạn.

Đưa image lên Docker Hub

Chia sẻ artifact sau khi build và kiểm thử

Registry lưu image để máy khác hoặc pipeline CI/CD tải lại mà không cần mã nguồn tại chỗ. Ví dụ với Docker Hub, bạn cần tài khoản và quyền push vào repository tương ứng.

  1. Build image của bạnHoàn thành lab chương 08–09 và xác nhận flask-counter:1.0 đã có trên máy.
  2. Đăng nhập registryChạy docker login rồi làm theo phương thức xác thực Docker hướng dẫn; ưu tiên access token / luồng đăng nhập an toàn.
  3. Đặt lại tên imageThay YOUR_USERNAME bằng Docker Hub username thật của bạn.
  4. Push và kiểm traPush image và kiểm tra repository trên Docker Hub. Quyền hiển thị public/private tùy cấu hình repository.
Terminal · thay YOUR_USERNAME trước khi chạy
docker image ls flask-counter
docker login

docker tag flask-counter:1.0 YOUR_USERNAME/flask-counter:1.0
docker push YOUR_USERNAME/flask-counter:1.0

# Máy khác có thể pull (nếu có quyền):
docker pull YOUR_USERNAME/flask-counter:1.0
Kiểm tra trước khi chia sẻ

Kiểm tra dependency, license, mã nguồn, biến môi trường, layer image và dữ liệu nhạy cảm. Một khi secret đã được đưa vào image rồi push, việc xóa tag không bảo đảm secret không còn bị lộ — phải thu hồi/xoay vòng secret ngay.

Trong dự án chuyên nghiệp, thường build, test, scan và push image trong CI/CD rồi triển khai bằng tag version/digest đã kiểm thử; không nên chỉ dựa vào tag latest.

16

Debug & lỗi thường gặp

Một quy trình tìm lỗi giúp tiết kiệm rất nhiều thời gian

Quy trình chẩn đoán nhanh

Terminal · dùng khi ứng dụng không lên
docker version
docker ps -a
docker logs --tail 100 TEN_CONTAINER
docker inspect TEN_CONTAINER
docker stats

# Nếu ứng dụng chạy bằng Compose:
docker compose ps
docker compose logs --tail 100 web
docker compose config
1. Cannot connect to the Docker daemon

Docker Engine chưa chạy, Docker Desktop chưa khởi động hoặc CLI đang trỏ sai context. Kiểm tra Docker Desktop/service và docker context ls. Trên Linux, kiểm tra sudo systemctl status docker.

2. permission denied khi chạy docker

Trên Linux có thể do user không có quyền tới Docker socket. Thử sudo docker ps để xác định nguyên nhân, rồi tham khảo hướng dẫn post-install/rootless. Không cấp quyền nhóm docker bừa bãi vì quyền này rất mạnh.

3. Bind for 0.0.0.0:8080 failed: port is already allocated

Một tiến trình/container khác đã chiếm cổng host. Kiểm tra docker ps, đổi sang cổng trống như 8082:80 hoặc dừng dịch vụ đang dùng cổng đó.

4. Container vừa chạy đã Exited

Container sống theo tiến trình chính. Kiểm tra docker logs TEN_CONTAINER, status và exit code bằng docker inspect. Nếu CMD chỉ in một dòng rồi kết thúc, đó có thể là hành vi đúng.

5. Truy cập localhost bị connection refused

Kiểm tra container còn chạy, port publish chính xác và app đang lắng nghe 0.0.0.0 bên trong container. Nếu app chỉ bind 127.0.0.1 bên trong container, host thường không truy cập được qua port mapping.

6. Web không kết nối được Redis/Postgres

Trong container, localhost không chỉ sang container database. Dùng hostname là service name (ví dụ redis), bảo đảm cùng network, database đã sẵn sàng và credentials/port đúng. Kiểm tra docker compose logs redis.

7. Đã sửa code nhưng container chạy code cũ

Image cũ vẫn đang được dùng. Với dự án build bằng Compose, thử docker compose up -d --build. Với bind mount, kiểm tra đường dẫn gắn volume đúng; không phải mọi server đều tự reload.

8. Dữ liệu biến mất sau khi xóa container

Có thể dữ liệu nằm trong writable layer mà không có volume, hoặc bạn đã dùng down -v. Kiểm tra docker volume ls, phần volumes của Compose và backup.

9. Docker build báo COPY failed hoặc không tìm thấy file

Kiểm tra bạn đang đứng ở đúng thư mục khi gọi docker build ... .. Đường dẫn COPY được tính theo build context; đồng thời kiểm tra .dockerignore có vô tình loại file cần thiết không.

10. No space left on device / image quá nhiều

Kiểm tra docker system df, image/volume có còn được dùng hay không, dữ liệu Docker Desktop đang lưu ở đâu. Dọn thận trọng bằng docker image prune hoặc các thao tác có mục tiêu; tránh lệnh prune toàn bộ khi chưa hiểu hậu quả.

11. Image không chạy trên CPU khác / exec format error

Kiểm tra image hỗ trợ nền tảng/kiến trúc cần dùng chưa, ví dụ amd64 so với arm64. Chọn image multi-platform hoặc dùng docker buildx phù hợp. Mô phỏng kiến trúc có thể ảnh hưởng hiệu năng.

12. Lệnh từ tutorial không chạy trên PowerShell

Bash dùng dấu \ để nối dòng; PowerShell dùng backtick hoặc gõ trên một dòng. Bash cũng dùng cú pháp biến môi trường khác PowerShell. Với lab, bạn có thể chép lệnh một dòng và chạy trong PowerShell hoặc WSL.

Về prune: dọn đúng thứ mình muốn dọn

Terminal · xem trước, dọn có chọn lọc
docker system df

docker container prune  # Xóa container đã dừng
docker image prune      # Xóa image không được dùng kiểu dangling
# Cẩn trọng với: docker volume prune / docker system prune --volumes
Không chạy dọn dẹp mù quáng

Trước khi prune, hãy kiểm tra các container, image và volume thật sự còn cần; dữ liệu bị xóa có thể không khôi phục được nếu không có backup.

Bài tập & tự kiểm tra

Kiểm chứng kiến thức bằng thao tác thật

Đánh dấu từng công việc khi bạn đã tự làm được. Danh sách ghi nhớ trên trình duyệt này (nếu trình duyệt cho phép lưu local storage khi mở file trực tiếp).

0/10 bài hoàn thành
Có thể quay lại làm tiếp bất kỳ lúc nào.

Câu hỏi tự kiểm tra

1. Khác nhau giữa docker run và docker start?

run tạo và chạy container mới; start khởi chạy một container đã tồn tại nhưng đang dừng.

2. EXPOSE 8000 có đồng nghĩa máy host truy cập cổng 8000 được ngay?

Không. EXPOSE chỉ mô tả cổng dự kiến. Cần publish phù hợp bằng -p/ports nếu muốn truy cập từ host.

3. Vì sao app dùng redis chứ không phải localhost để kết nối database?

Trong mạng Compose, hostname redis được DNS nội bộ phân giải tới container service Redis; localhost bên trong web chỉ trỏ tới web.

4. Điều gì xảy ra khi chạy docker compose down -v?

Compose xóa container, network liên quan và các named volumes do project quản lý theo tùy chọn -v; dữ liệu volume có thể bị mất.

5. Dockerfile chạy USER appuser nhằm mục đích gì?

Để tiến trình ứng dụng không mặc định chạy dưới root, qua đó giới hạn một số quyền không cần thiết. Đây là một biện pháp giảm thiểu, không phải bảo đảm an toàn tuyệt đối.

6. Khi nào nên dùng multi-stage build?

Khi build cần thêm compiler/tool/source trung gian nhưng runtime chỉ cần artifact đã tạo; multi-stage giúp giữ image chạy cuối gọn hơn.

Bài tập nâng cấp

  1. Đổi cổng host từ 8000 sang 8088 trong Compose rồi chạy lại.
  2. Thêm route /about vào Flask, rebuild image và kiểm tra response mới.
  3. Thêm Redis health check nếu bạn tự dựng stack khác từ đầu.
  4. Kiểm tra dung lượng image trước/sau khi đổi Dockerfile; ghi lại số liệu, không tối ưu bằng cảm giác.
  5. Viết file README mô tả cách build, start, xem log, backup và dừng dự án.
