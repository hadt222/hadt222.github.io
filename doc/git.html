CHƯƠNG 01

Git, GitHub và GitLab là gì?

Hiểu đúng vai trò trước khi học câu lệnh.

Git là hệ thống quản lý phiên bản phân tán (DVCS). Nó ghi lại các snapshot của dự án theo commit, cho phép xem lịch sử, thử nghiệm trên nhánh và cộng tác mà không phải sao chép các thư mục kiểu final_v2_really_final.

⌘

Git

Phần mềm chạy trên máy của bạn: repository, commit, branch, merge, rebase, tag và lịch sử.

CLI: git
◉

GitHub

Dịch vụ lưu trữ repository và cộng tác: Pull Request, review, Issues, Actions, Releases.

CLI bổ sung: gh
◆

GitLab

Nền tảng repository và DevSecOps: Merge Request, Issues, GitLab CI/CD, branch rules.

CLI bổ sung: glab
Công cụVai trò chínhDùng để làm gì?
gitMáy tính / repositoryQuản lý phiên bản và lịch sử mã nguồn
GitHubMáy chủ / webLưu trữ, Pull Request, review, GitHub Actions
GitLabMáy chủ / webLưu trữ, Merge Request, GitLab CI/CD
✓
Thực hành tốt

Git không cần Internet để tạo commit, nhánh hay xem lịch sử; bạn chỉ cần mạng khi tương tác với máy chủ từ xa. GitHub và GitLab đều dùng Git, nhưng PR/MR và CI/CD là chức năng nền tảng, không phải lệnh Git thuần.

CHƯƠNG 02

Mô hình hoạt động của Git

Working Directory → Staging Area → Local Repository → Remote.

Bốn khu vực sau là chìa khóa để hiểu phần lớn lệnh Git. Staging Area (còn gọi là index) cho phép lựa chọn chính xác những thay đổi sẽ nằm trong commit tiếp theo.

01Working directoryChỉnh sửa tập tin
→git add
02Staging areaChọn nội dung commit
→git commit
03Local repoSnapshot & history
→git push
04Remote repoGitHub / GitLab
Terminal · Bash / zsh
git status                  # Xem tập tin đã sửa, staged, chưa theo dõi
git add src/main.py         # Đưa một tập tin vào staging area
git diff --staged           # Xem các thay đổi sẽ được commit
git commit -m "feat: add feature"  # Tạo commit ở máy local
git push                    # Đưa commit lên remote (sau khi thiết lập upstream)

Git theo dõi tập tin như thế nào?

untracked: tập tin mới, Git chưa quản lý; modified: đã thay đổi; staged: nội dung đã chọn cho commit; committed: snapshot được lưu.

HEAD, branch, commit

HEAD thường trỏ đến branch hiện tại; branch trỏ tới commit đầu nhánh. Một commit tham chiếu đến snapshot và commit cha, tạo nên lịch sử của repository.

CHƯƠNG 03

Cài đặt và cấu hình ban đầu

Hướng dẫn cho macOS, Windows và Linux.

macOS

macOS · zsh
xcode-select --install    # Nếu máy chưa có Command Line Tools
brew install git           # Nếu đã cài Homebrew
git --version

Windows / Linux

Windows · Linux
# Windows PowerShell (nếu có winget)
winget install --id Git.Git -e
# Ubuntu / Debian
sudo apt update && sudo apt install git
# Kiểm tra
git --version

Thiết lập danh tính commit

Terminal · Bash / zsh
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"   # Nếu có VS Code
git config --list --show-origin

--global áp dụng mặc định cho người dùng hiện tại. Muốn dùng email riêng trong dự án công ty, vào thư mục repository và cấu hình git config user.email "work@example.com" (bỏ --global).

✦
Mẹo

Tên và email trong Git là metadata của commit, không phải mật khẩu đăng nhập GitHub/GitLab. Với môi trường máy doanh nghiệp, kiểm tra chính sách của tổ chức trước khi thay cấu hình.

CHƯƠNG 04

Tạo repository và commit đầu tiên

Bài thực hành bắt đầu từ một thư mục trống.

  1. Tạo thư mục và khởi tạo Git. Lệnh git init -b main đặt tên branch ban đầu là main.
  2. Tạo README, xem trạng thái. Git sẽ báo một tập tin chưa được theo dõi.
  3. Stage và commit. Mỗi commit nên diễn đạt một thay đổi có ý nghĩa.
Terminal · Bash / zsh
mkdir git-lab
cd git-lab
git init -b main

echo "# Git Lab" > README.md
git status
git add README.md
git diff --staged
git commit -m "docs: add initial README"

git log --oneline --decorate
git status

Hai cách khởi tạo thường gặp

LệnhKhi nào sử dụng?
git initBiến một thư mục hiện có thành repository local
git clone <URL>Sao chép repository đã có từ máy chủ về máy
ⓘ
Ghi nhớ

Dấu <...> trong tutorial là placeholder, không nhập cả dấu ngoặc. Ví dụ USERNAME, GROUP, REPO cần thay bằng tài khoản và tên dự án thực tế.

CHƯƠNG 05

Các lệnh Git cơ bản nhất

Chu kỳ làm việc hằng ngày: status → diff → add → commit → log.

Kiểm tra và ghi nhận thay đổi

Terminal · Bash / zsh
git status                      # Trạng thái hiện tại
git status -sb                  # Bản rút gọn, kèm branch
git diff                        # Thay đổi chưa stage
git diff --staged               # Thay đổi đã stage
git add file.txt                # Stage một tập tin
git add .                       # Stage thay đổi trong thư mục hiện tại
git add -p                      # Chọn từng đoạn thay đổi (hunk)
git commit -m "fix: handle empty input"
git log --oneline -10          # 10 commit gần nhất
git show HEAD                   # Nội dung commit hiện tại

Quản lý tập tin

Terminal · Bash / zsh
git mv old.py new.py            # Đổi tên, đưa thay đổi vào staging
git rm obsolete.txt             # Xóa tập tin được theo dõi và stage
git ls-files                    # Danh sách tập tin Git đang theo dõi
git check-ignore -v .env        # Lý do tập tin bị ignore (nếu có)
✓
Thực hành tốt

Không dùng git add . một cách máy móc. Kiểm tra git status và git diff --staged trước khi commit để tránh đưa file nhạy cảm hay file sinh tự động vào repository.

CHƯƠNG 06

Branch, switch và merge

Phát triển tính năng độc lập với nhánh chính.

Branch là con trỏ nhẹ tới commit. Thông lệ là tạo nhánh riêng cho từng tính năng hoặc bản sửa lỗi rồi hợp nhất sau khi kiểm tra.

Terminal · Bash / zsh
git branch                           # Xem các branch local
git branch -a                        # Local + remote-tracking branches
git switch -c feature/login          # Tạo và chuyển sang nhánh mới
git switch main                      # Trở về nhánh main
git switch feature/login             # Chuyển sang nhánh có sẵn
git branch -m feature/sign-in        # Đổi tên branch hiện tại
git branch -d feature/sign-in        # Xóa branch đã merge

Ví dụ merge một tính năng

Terminal · Bash / zsh
git switch -c feature/about
# Chỉnh sửa một tập tin, ví dụ README.md
git add README.md
git commit -m "docs: add about section"

git switch main
git merge feature/about
git branch -d feature/about
Minh họa lịch sử
main trước merge:    A ── B ── C
                           \
feature/about:               D ── E

merge commit (nếu cần): A ── B ── C ── M
                           \       /
                            D ── E
Git cũng có thể fast-forward nếu nhánh đích không có commit mới kể từ khi tách nhánh.

Merge và Rebase khác nhau thế nào?

Phương phápCách vận hànhLưu ý
MergeKết hợp lịch sử, có thể tạo merge commitGiữ cấu trúc phát triển song song; phù hợp nhánh dùng chung
RebasePhát lại commit lên một base mớiLịch sử tuyến tính; commit hash thay đổi
Terminal · Bash / zsh
git fetch origin
git switch feature/login
git rebase origin/main          # Cập nhật feature lên main mới nhất
# Nếu có conflict: sửa file → git add file → git rebase --continue
git rebase --abort             # Hủy rebase đang chạy
⚠
Thận trọng

Không rebase tùy tiện các commit đã được người khác sử dụng chung. Khi buộc cập nhật remote của nhánh cá nhân sau rebase, cân nhắc git push --force-with-lease, không dùng --force trên nhánh được chia sẻ.

CHƯƠNG 07

Remote, clone, fetch, pull và push

Đồng bộ repository giữa máy local và GitHub/GitLab.

origin là tên remote phổ biến được git clone tự đặt. upstream thường dùng để gọi repository gốc khi bạn làm việc bằng fork; đây chỉ là quy ước tên, không phải từ khóa cố định.

Terminal · Bash / zsh
git remote -v                      # Liệt kê remote + URL
git remote add origin URL          # Gắn remote mới
git remote set-url origin NEW_URL  # Thay URL remote
git clone URL                      # Tải repo về máy
git fetch origin                   # Lấy metadata/commit, chưa merge
git pull --ff-only origin main     # Fetch + fast-forward nếu có thể
git pull --rebase origin main      # Fetch rồi rebase commit local
git push -u origin main            # Đẩy branch và đặt upstream
git push                          # Push tới upstream đã cấu hình
git push origin feature/login      # Push branch cụ thể

Phân biệt các lệnh đồng bộ

LệnhTác dụngĐiểm cần nhớ
fetchTải commit/ref từ remote, không tự nhập vào branch đang làm việcAn toàn để xem trước thay đổi
pullFetch rồi tích hợp bằng merge/rebase/fast-forward tùy tùy chọn và cấu hìnhCó thể phát sinh conflict
pushCập nhật nhánh remote bằng commit ở máy localCó thể bị từ chối nếu nhánh remote đã tiến lên
ⓘ
Ghi nhớ

Nếu git pull báo divergent branches, hãy quyết định rõ chiến lược: --rebase, --no-rebase hoặc --ff-only; tránh chọn theo thói quen mà chưa hiểu lịch sử commit.

CHƯƠNG 08

GitHub từ A đến Z

Repository, Pull Request, Issues, review và GitHub CLI.

Đưa repository local lên GitHub

Trên GitHub, tạo repository rỗng tên git-lab. Nếu bạn đã có commit local, nên bỏ chọn tạo README/license/gitignore lúc tạo repo để tránh lịch sử ban đầu khác nhau.

Terminal · Bash / zsh
# HTTPS (thay USERNAME bằng GitHub username)
git remote add origin https://github.com/USERNAME/git-lab.git
git push -u origin main

# Hoặc: SSH
git remote set-url origin git@github.com:USERNAME/git-lab.git
git push -u origin main

GitHub CLI (gh)

gh không thay thế git; nó thao tác với tính năng của GitHub qua terminal. Cài bằng cli.github.com hoặc brew install gh trên macOS.

Terminal · Bash / zsh
gh auth login                         # Đăng nhập GitHub
# Trong repo local, nếu chưa có remote:
gh repo create git-lab --private --source=. --remote=origin --push

git switch -c feature/new-homepage
# Sửa file, add và commit
git push -u origin feature/new-homepage
gh pr create --fill                   # Tạo Pull Request

gh pr list                            # Danh sách PR
gh pr view --web                      # Mở PR hiện tại trên web
gh pr checks                          # Kiểm tra CI của PR
gh issue list                         # Danh sách issue
gh repo view --web                    # Mở repository

Quy trình Pull Request

  1. Tạo feature/... từ main đã cập nhật.
  2. Thực hiện commit nhỏ, có ý nghĩa; push nhánh lên GitHub.
  3. Tạo Pull Request (PR), mô tả mục đích, cách kiểm thử và ảnh hưởng.
  4. Code review, chạy CI, sửa theo góp ý và merge khi đủ điều kiện.
  5. Cập nhật main local và xóa nhánh đã hoàn thành.
✦
Mẹo

Có thể chọn Merge commit, Squash merge hoặc Rebase merge tùy quy tắc của repository. Branch protection/rulesets có thể yêu cầu review và CI thành công trước khi merge.

CHƯƠNG 09

GitLab từ A đến Z

Project, Merge Request, pipeline và GitLab CLI.

Trong GitLab, repository thường nằm trong một project, có thể thuộc tài khoản cá nhân hoặc một group. Quy trình giống GitHub nhưng đề xuất thay đổi được gọi là Merge Request (MR).

Đẩy code lên GitLab

Terminal · Bash / zsh
# Tạo project rỗng trên GitLab trước
git remote add origin https://gitlab.com/GROUP/REPO.git
git push -u origin main

# Nếu dùng SSH
git remote set-url origin git@gitlab.com:GROUP/REPO.git

GitLab CLI (glab)

Cài từ GitLab CLI hoặc brew install glab nếu dùng Homebrew.

Terminal · Bash / zsh
glab auth login                 # Đăng nhập GitLab
glab repo view                  # Xem repository / project
glab mr create --fill           # Tạo Merge Request từ branch hiện tại
glab mr list                    # Danh sách Merge Request
glab mr view                    # Xem thông tin MR
glab issue list                 # Danh sách issue
glab pipeline list              # Xem pipeline
glab ci status                  # Trạng thái CI nếu phiên bản hỗ trợ

Branch protection và merge

Cấu hình quyền nhánh tại Settings → Repository → Branch rules (tùy quyền và phiên bản GitLab). Nên bảo vệ main, yêu cầu MR và kiểm thử tự động cho các thay đổi quan trọng.

ⓘ
Ghi nhớ

Nền tảng GitLab.com và GitLab Self-Managed có thể khác nhau về địa chỉ máy chủ, chính sách quyền và tính năng theo gói. Với server riêng, đăng nhập bằng glab auth login và chọn đúng instance.

CHƯƠNG 10

HTTPS, SSH và bảo mật tài khoản

Thiết lập kết nối đúng cách, tránh lộ credential.

HTTPS hay SSH?

Giao thứcVí dụ URLCách xác thực
HTTPShttps://github.com/USER/REPO.gitThường dùng credential manager, CLI hoặc token
SSHgit@github.com:USER/REPO.gitXác thực bằng cặp khóa SSH; phù hợp sử dụng thường xuyên

Tạo và đăng ký SSH key

Terminal · Bash / zsh
ls -al ~/.ssh                    # Xem key đã có trước
ssh-keygen -t ed25519 -C "you@example.com"
eval "$(ssh-agent -s)"             # Bash/zsh trên macOS hoặc Linux
ssh-add ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub         # Chỉ sao chép PUBLIC KEY

ssh -T git@github.com             # Kiểm tra kết nối GitHub
ssh -T git@gitlab.com             # Kiểm tra kết nối GitLab

Thêm nội dung của id_ed25519.pub trong phần SSH keys của tài khoản. Tập tin id_ed25519 không có đuôi .pub là private key và không được chia sẻ. Lần đầu kết nối cần kiểm tra fingerprint/host key với tài liệu chính thức.

GitHub CLI và GitLab CLI

Terminal · Bash / zsh
gh auth login
  # Chọn tài khoản, giao thức và cách đăng nhập tương ứng
gh auth status

glab auth login
glab auth status
⚠
Thận trọng

Không đưa mật khẩu, API token, private key, file .env hay khóa dịch vụ lên Git. Nếu bí mật đã bị commit/push, hãy thu hồi hoặc xoay vòng credential ngay; xóa ở commit mới không làm mất nội dung khỏi lịch sử cũ.

CHƯƠNG 11

Merge conflict và cách xử lý

Phát hiện, chỉnh sửa, đánh dấu resolved và hoàn tất.

Conflict xảy ra khi Git không thể tự quyết định cách kết hợp các thay đổi (thường cùng vùng văn bản của một file). Khi đó, file có thể chứa các dấu phân cách:

Ví dụ · Nội dung file khi có conflict
<<<<<<< HEAD
print("Hello from main")
=======
print("Hello from feature")
>>>>>>> feature/greeting

Bạn phải sửa thành nội dung mong muốn (bỏ toàn bộ marker), chạy thử chương trình rồi stage file để đánh dấu đã giải quyết.

Terminal · Bash / zsh
git status                      # Xem file bị conflict
# Mở file, chỉnh sửa và xóa các dòng <<<<<<<, =======, >>>>>>>
git add app.py                  # Đánh dấu đã giải quyết
git commit                      # Hoàn tất merge đang dở

# Hoặc nếu muốn hủy merge:
git merge --abort

Nếu conflict xảy ra khi rebase

Terminal · Bash / zsh
git status
# Sửa conflict rồi:
git add app.py
git rebase --continue           # Chuyển sang commit rebase tiếp theo
# Nếu muốn hủy toàn bộ rebase đang chạy:
git rebase --abort
⚠
Thận trọng

Trong quá trình rebase, ý nghĩa ours/theirs có thể khác trực giác so với merge. Đọc nội dung và kiểm tra kết quả thay vì chọn một phía một cách mù quáng.

CHƯƠNG 12

Undo: restore, reset, revert và reflog

Chọn đúng cách hoàn tác tùy nội dung đã commit hoặc push.

Đây là nhóm lệnh dễ gây mất dữ liệu nhất. Hãy xác định thứ bạn muốn hủy: thay đổi chưa stage, staged changes, commit local hay commit đã chia sẻ.

Mục tiêuLệnhMức độ lưu ý
Bỏ sửa ở working directorygit restore file.txtMất sửa đổi chưa commit
Bỏ khỏi staginggit restore --staged file.txtGiữ file đã sửa
Sửa commit cuối (chưa chia sẻ)git commit --amendViết lại commit
Gỡ commit local, giữ stagedgit reset --soft HEAD~1Viết lại lịch sử local
Hoàn tác commit đã pushgit revert COMMIT_HASHTạo commit đảo ngược
Bỏ commit và thay đổigit reset --hard HEAD~1Nguy cơ mất dữ liệu
Terminal · Bash / zsh
git restore --staged config.py       # Unstage, giữ nội dung file
git restore config.py                # Bỏ sửa chưa stage trong file
git commit --amend -m "fix: clearer message"
git reset --soft HEAD~1             # Bỏ commit cuối, giữ staged
git revert a1b2c3d                  # Tạo commit đảo ngược commit cụ thể

git reflog                           # Lịch sử vị trí HEAD/refs gần đây
git branch rescue BRANCH_OR_HASH     # Tạo nhánh cứu hộ từ hash còn tồn tại

Xóa tập tin chưa theo dõi bằng git clean

Terminal · Bash / zsh
git clean -nd     # Dry run: xem sẽ xóa những gì
git clean -fd     # NGUY HIỂM: thực sự xóa untracked files/dirs
⚠
Thận trọng

Ưu tiên git revert với commit đã push lên nhánh dùng chung. Trước lệnh reset --hard hoặc clean -fd, hãy sao lưu thay đổi cần giữ và kiểm tra git status. reflog không bảo đảm phục hồi mọi nội dung chưa từng được commit.

CHƯƠNG 13

Stash, tag, cherry-pick và công cụ nâng cao

Những lệnh hữu ích khi làm dự án thực tế.

Stash — cất thay đổi tạm

Terminal · Bash / zsh
git stash push -u -m "wip: login page"   # Cất cả untracked files
git stash list
git stash show -p stash@{0}
git stash pop                            # Áp dụng rồi xóa nếu thành công
# git stash apply stash@{0}             # Áp dụng nhưng vẫn giữ stash

Tag — đánh dấu phiên bản phát hành

Terminal · Bash / zsh
git tag -a v1.0.0 -m "Release v1.0.0"
git tag --list
git push origin v1.0.0
git show v1.0.0

Cherry-pick, bisect, worktree

Terminal · Bash / zsh
git cherry-pick COMMIT_HASH       # Chép một commit sang nhánh hiện tại
git bisect start                  # Bắt đầu tìm commit gây lỗi
git bisect bad                    # Phiên bản hiện tại bị lỗi
git bisect good GOOD_HASH         # Phiên bản cũ còn tốt
# Test theo chỉ dẫn của Git, đánh dấu good/bad sau mỗi lần
git bisect reset                  # Trở về trạng thái trước bisect

git worktree add ../hotfix -b hotfix/urgent main
# Làm việc tại ../hotfix, commit và xử lý branch đó
git worktree list                 # Các working tree
git worktree remove ../hotfix     # Xóa worktree khi đã sạch

Xem lịch sử và so sánh

Terminal · Bash / zsh
git log --oneline --graph --all --decorate
git log --author="Your Name" --since="2 weeks ago"
git blame app.py                 # Ai sửa mỗi dòng (cần diễn giải có ngữ cảnh)
git diff main...feature/login   # So sánh từ merge base đến tip feature
git show COMMIT_HASH:path/to/file.py
✦
Mẹo

Với model weights, video hay dữ liệu lớn, cân nhắc Git LFS hoặc hệ thống lưu trữ dữ liệu phù hợp. Không nên commit trực tiếp kho dữ liệu lớn hay secrets vào Git.

CHƯƠNG 15

GitHub Actions và GitLab CI/CD

Tự động kiểm tra code khi push hoặc tạo PR/MR.

CI (Continuous Integration) chạy kiểm tra tự động sau thay đổi code; CD thường đề cập tự động phân phối hoặc triển khai. Pipeline cần runner/agent thực thi và quyền truy cập phù hợp.

GitHub Actions: .github/workflows/ci.yml

GitHub Actions · YAML
name: Basic CI
on: [push, pull_request]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Verify README exists
        run: test -f README.md

GitLab CI/CD: .gitlab-ci.yml

GitLab CI/CD · YAML
stages:
  - test

check_readme:
  stage: test
  image: alpine:3.20
  script:
    - test -f README.md

Hai ví dụ chỉ kiểm tra sự tồn tại của README.md, phù hợp để học pipeline. Khi áp dụng thực tế, thay bằng pytest, npm test, lint hoặc build, và kiểm soát secrets bằng cơ chế riêng của nền tảng.

GitHub

Workflow YAML nằm trong .github/workflows/; kiểm tra kết quả tại tab Actions.

GitLab

Pipeline YAML nằm ở gốc repository với tên .gitlab-ci.yml; theo dõi tại Build → Pipelines (giao diện có thể đổi).

⚠
Thận trọng

Với các action/package dùng trong sản xuất, hãy kiểm soát version/digest, phân quyền token tối thiểu và không in secrets ra log. File workflow là code có khả năng thực thi trên runner.

CHƯƠNG 18

Bài lab hoàn chỉnh: từ local đến PR/MR

Thực hành theo trình tự, có kết quả mong đợi.

30–45 phútNgười mớimacOS / Linux / Git Bash

Phần A. Tạo project và hai commit

Terminal · Bash / zsh
mkdir todo-demo && cd todo-demo
git init -b main
printf "# Todo Demo\n" > README.md
git add README.md
git commit -m "docs: initialize project"

git switch -c feature/todo-list
printf "- [ ] Learn Git\n" >> README.md
git add README.md
git commit -m "feat: add sample todo item"
git log --oneline --all --graph --decorate

Kết quả: Có hai commit, trong đó commit thứ hai nằm trên nhánh feature/todo-list; main vẫn ở commit ban đầu.

Phần B. Đưa nhánh lên GitHub hoặc GitLab

Terminal · Bash / zsh
# Sau khi tạo repository rỗng trên host, chọn MỘT URL:
# GitHub:
git remote add origin https://github.com/USERNAME/todo-demo.git
# Hoặc GitLab:
# git remote add origin https://gitlab.com/USERNAME/todo-demo.git

git push -u origin main
git push -u origin feature/todo-list
# Trên web mở Pull Request (GitHub) hoặc Merge Request (GitLab)

Kết quả: Remote có hai nhánh; mở PR/MR để hợp nhất feature/todo-list vào main. Repo phải được tạo rỗng trước, có quyền push và xác thực thành công.

Phần C. Sau khi PR/MR được merge

Terminal · Bash / zsh
git switch main
git pull --ff-only origin main
git branch -d feature/todo-list
# Nếu cần xóa branch remote còn tồn tại:
# git push origin --delete feature/todo-list

git tag -a v0.1.0 -m "First tutorial release"
git push origin v0.1.0
git status

Kết quả: main local đã chứa thay đổi sau merge; tag v0.1.0 đã được push lên máy chủ. Nếu team dùng squash merge, branch local có thể không được coi là merged nguyên vẹn: kiểm tra nội dung trước khi dùng git branch -D.

✦
Mẹo
