01

REST API là gì?

Nắm 3 khái niệm: API, HTTP và REST — chúng có liên quan nhưng không giống nhau.

API (Application Programming Interface) là giao diện giúp hai hệ thống phần mềm giao tiếp. HTTP là giao thức thường được dùng để gửi yêu cầu và nhận phản hồi trên web. REST (Representational State Transfer) là phong cách kiến trúc do Roy Fielding mô tả, đặt ra các ràng buộc để hệ thống phân tán dễ mở rộng và tương tác.

REST API thường là một HTTP API tổ chức dữ liệu quanh tài nguyên (resource), định danh bằng URL, thao tác bằng HTTP methods, biểu diễn dữ liệu thường bằng JSON. Tuy nhiên REST không đồng nghĩa với JSON hoặc CRUD; một API dùng JSON/HTTP chưa chắc đáp ứng đầy đủ các ràng buộc REST.

02

Sáu ràng buộc của REST

Đây là nền tảng kiến trúc; chúng không chỉ là danh sách các HTTP methods.

01 · Bắt buộc

Client–Server

Tách giao diện người dùng khỏi nơi lưu trữ và xử lý dữ liệu. Mỗi bên có thể phát triển độc lập.

02 · Bắt buộc

Stateless

Mỗi request chứa đủ thông tin cần thiết. Server không dựa vào trạng thái phiên hội thoại của request trước để hiểu request hiện tại.

03 · Bắt buộc

Cacheable

Response xác định được có thể cache hay không, giúp giảm độ trễ và tải máy chủ.

04 · Bắt buộc

Uniform Interface

Giao diện thống nhất: resource có định danh, thao tác qua biểu diễn, thông điệp tự mô tả và điều hướng bằng hypermedia.

05 · Bắt buộc

Layered System

Client không cần biết nó giao tiếp trực tiếp với server gốc hay qua proxy, gateway, load balancer.

06 · Tùy chọn

Code on Demand

Server có thể truyền mã thực thi cho client khi phù hợp; đây là ràng buộc tùy chọn.

Điểm thường bị bỏ qua: HATEOASHypermedia as the Engine of Application State là một phần của uniform interface. Nhiều API được gọi là “REST API” trong thực tế là REST-like HTTP APIs vì không triển khai đầy đủ hypermedia.
03

Resource, URL và endpoint

Thiết kế URL theo danh từ (tài nguyên), dùng HTTP method để thể hiện thao tác.

Giả sử hệ thống có tasks (công việc) và users (người dùng). Một collection và một item thường có đường dẫn như sau:

EndpointÝ nghĩaVí dụ

/api/v1/tasks/42Một công việc có ID = 42Đọc, sửa hoặc xóa
/api/v1/users/7/tasksCông việc thuộc user 7Đọc danh sách theo quan hệ

Nên làm ✓GET /tasks
POST /tasks
GET /tasks/42

Nên tránh ✕GET /getAllTasks

Động từ trong URL cho thao tác CRUD thông thường.

Không phải mọi nghiệp vụ đều ánh xạ gọn vào CRUD. Các hành động như “thanh toán” có thể được mô hình hóa thành tài nguyên mới như POST /payments hoặc POST /orders/42/cancellations.

04

HTTP methods: GET, POST, PUT, PATCH, DELETE

Mỗi method có ý nghĩa riêng. Chọn sai method dễ gây lỗi cache, retry và bảo mật.

MethodCông dụng phổ biếnSafe?Idempotent?Ví dụ
GETĐọc resourceCóCóGET /tasks/1
POSTGửi dữ liệu/tạo resource dưới collectionKhôngKhông đảm bảoPOST /tasks
PUTTạo/thay thế trạng thái resource tại URI đíchKhôngCóPUT /tasks/1
PATCHSửa một phần resourceKhôngKhông đảm bảoPATCH /tasks/1
DELETEXóa liên kết tới resourceKhôngCóDELETE /tasks/1
HEADNhư GET nhưng không có response bodyCóCóHEAD /tasks/1
OPTIONSHỏi khả năng giao tiếp, dùng trong CORS preflightCóCóOPTIONS /tasks

Safe và idempotent khác nhau thế nào?

Safe nghĩa là request không yêu cầu thay đổi trạng thái server (GET có thể vẫn được ghi log). Idempotent nghĩa là thực hiện cùng một request nhiều lần có cùng hiệu ứng dự định lên trạng thái server như một lần. Ví dụ DELETE lần đầu có thể trả 204, lần tiếp theo trả 404, nhưng resource vẫn bị xóa — do đó DELETE vẫn idempotent.

PUT so với PATCH

PUT

Gửi biểu diễn đầy đủ của task: {"title":"A","completed":true}. Trong API ví dụ bên dưới, thiếu một trường là lỗi 400.

PATCH

Chỉ gửi thay đổi: {"completed":true}. Ngữ nghĩa PATCH phụ thuộc định dạng patch mà API định nghĩa.

Ghi nhớPOST thường tạo dưới collection nhưng không chỉ dùng để tạo; PUT không nhất thiết chỉ dùng cập nhật; PATCH không mặc định idempotent. Cần đọc hợp đồng API cụ thể.
05

Một HTTP request & response gồm gì?

Hiểu phương thức, path, query, headers, body và mã trạng thái của phản hồi.

Ví dụ: request đọc danh sách

HTTP REQUEST · MINH HỌA
GET /api/v1/tasks?completed=false&page=1&limit=10 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <access_token>

GET là method; /api/v1/tasks là path; ?completed=false&page=1&limit=10 là query string; Accept thông báo định dạng phản hồi mong muốn; Authorization mang thông tin xác thực (nếu API yêu cầu).

Ví dụ: response trả JSON

HTTP RESPONSE · MINH HỌA
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: private, max-age=60

{
  "data": [
    { "id": 1, "title": "Học REST API", "completed": false },
    { "id": 2, "title": "Viết API đầu tiên", "completed": false }
  ],
  "pagination": { "page": 1, "limit": 10, "total": 2 }
}

Response gồm status line (HTTP/1.1 200 OK), headers và body. JSON dùng object {}, array [], chuỗi, số, boolean và null. Đây là ví dụ mô phỏng, không phải dữ liệu của API công khai.

Request tạo dữ liệu và phản hồi

POST · REQUEST
POST /api/v1/tasks HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "title": "Hoàn thành bài tập REST API",
  "completed": false
}
201 · RESPONSE
HTTP/1.1 201 Created
Location: /api/v1/tasks/3
Content-Type: application/json

{
  "id": 3,
  "title": "Hoàn thành bài tập REST API",
  "completed": false
}
Content-Type vs AcceptContent-Type: application/json mô tả định dạng nội dung gửi đi; Accept: application/json cho biết client muốn nhận định dạng nào. GET thường không có request body.

HTTP status codes quan trọng

Đọc status trước khi đọc body: thành công, lỗi phía client hay lỗi phía server?

2xx · Success

Yêu cầu thành công

Đọc, tạo mới, cập nhật hoặc xóa thành công.

4xx · Client error

Yêu cầu có vấn đề

Sai dữ liệu, thiếu quyền, không tìm thấy, vượt giới hạn.

5xx · Server error

Trả lỗi có cấu trúc: Problem Details

Có thể dùng chuẩn RFC 9457 với media type application/problem+json, bao gồm các trường phổ biến type, title, status, detail, instance:

APPLICATION/PROBLEM+JSON
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Dữ liệu không hợp lệ",
  "status": 422,
  "detail": "Trường title phải là chuỗi không rỗng.",
  "instance": "/api/v1/tasks"
}

API Express trong bài dùng định dạng lỗi đơn giản {"error":"..."} để dễ học; bạn có thể nâng cấp sang Problem Details khi xây dự án thật.

07

Thiết kế REST API dễ dùng

Quy ước URL rõ ràng, danh sách có thể lọc/sắp xếp, phản hồi nhất quán và dễ mở rộng.

Path parameter và query parameter

LoạiVí dụDùng khi
Path parameter/tasks/42Định danh một resource cụ thể
Query: filter/tasks?completed=falseLọc tập hợp
Query: sort/tasks?sort=-created_atSắp xếp giảm dần theo thời điểm tạo (quy ước của API)
Query: pagination/tasks?page=2&limit=20Phân trang
Query: search/tasks?q=restTìm theo từ khóa

Phân trang: offset vs cursor

Page / offset

?page=3&limit=20

Dễ hiểu, phù hợp danh sách nhỏ hoặc cần nhảy đến trang cụ thể. Dữ liệu thêm/xóa liên tục dễ làm trùng/thiếu item giữa các lần phân trang.

Cursor

?cursor=...&limit=20

Phù hợp feed lớn hoặc dữ liệu biến động, cần thứ tự ổn định và cursor do server cấp. Không nên tự diễn giải cursor từ phía client.

VÍ DỤ CURSOR PAGINATION (MINH HỌA)
GET /api/v1/tasks?limit=20&cursor=eyJpZCI6MTAwfQ

{
  "data": [{ "id": 101, "title": "Task minh họa", "completed": false }],
  "next_cursor": "eyJpZCI6MTIwfQ",
  "has_more": true
}

Quy tắc gợi ý

  • Đặt tên collection nhất quán, ví dụ /tasks.
  • Giữ đường dẫn dễ dự đoán, tránh lồng quá sâu.
  • Dùng đúng status code và cấu trúc lỗi.
  • Giới hạn số phần tử tối đa mỗi trang.
  • Hỗ trợ filter/sort khi có nhu cầu thật.
  • Không làm thay đổi dữ liệu qua GET.
  • Áp dụng versioning khi cần thay đổi phá vỡ tương thích.
  • Viết tài liệu và ví dụ request/response.
Versioning/api/v1/tasks là cách phổ biến, dễ nhìn. Ngoài URL version còn có version qua header/media type. Chọn một chính sách và công bố rõ khi nào nâng phiên bản.
08

Authentication, Authorization, CORS và bảo mật

Không chỉ làm cho API hoạt động, mà còn phải giới hạn ai được làm gì và bảo vệ dữ liệu.

Authentication

"Bạn là ai?"

Xác minh danh tính, ví dụ dùng phiên đăng nhập hoặc OAuth 2.0 access token. Header thường gặp: Authorization: Bearer ....

Authorization

"Bạn được phép làm gì?"

Kiểm tra quyền trên từng hành động và từng resource: user A không tự động được xem/sửa dữ liệu của user B.

CORS là gì?

Cross-Origin Resource Sharing là cơ chế dựa trên HTTP headers để trình duyệt quyết định liệu JavaScript từ origin A có được đọc phản hồi của origin B không. Một số request cần preflight bằng OPTIONS trước request chính. CORS không thay thế xác thực, phân quyền và bảo vệ API phía server; các client không phải trình duyệt không bị hạn chế theo cách tương tự.

Không đưa bí mật vào front-endAPI key bí mật, private key và mật khẩu không được nhúng vào HTML/JavaScript công khai. Token cần được bảo vệ phù hợp; đừng log thông tin nhạy cảm. Luôn dùng HTTPS trong production.

Checklist bảo mật tối thiểu

  • HTTPS: mã hóa giao tiếp, tránh lộ token khi truyền.
  • Validate input: kiểm tra kiểu, độ dài, dữ liệu được phép; không tin dữ liệu từ client.
  • Authorize từng resource: không chỉ kiểm tra người dùng đã đăng nhập.
  • Rate limiting: hạn chế lạm dụng; sử dụng 429 khi phù hợp.
  • Giới hạn kích thước body và thiết lập timeout hợp lý.
  • Cấu hình CORS có chủ đích: chỉ cho phép những origin cần thiết.
  • Không để lộ stack trace và thông tin nội bộ trong response lỗi.

Tự xây REST API với Node.js + Express

Ví dụ chạy được trên máy tính: một CRUD API quản lý công việc.

Ví dụ này dùng Node.js và framework Express. Dữ liệu lưu trong mảng RAM cho dễ học: khởi động lại server sẽ mất thay đổi. Trong dự án thực tế, thay bằng cơ sở dữ liệu, thêm authentication, authorization, log, test và cơ chế chống lỗi.

Bước 1 · Tạo project

cd rest-api-demo

Bước 2 · Viết file server.js

SERVER.JS · EXPRESS API
// server.js — Node.js + Express; dữ liệu chỉ nằm trong RAM
const express = require('express');
const app = express();
app.use(express.json());

let tasks = [
  { id: 1, title: 'Học REST API', completed: false },
  { id: 2, title: 'Thực hành curl', completed: true }
];
let nextId = 3;

const byId = (id) => tasks.find(t => t.id === Number(id));
const validTitle = (v) => typeof v === 'string' && v.trim().length > 0;
const validCompleted = (v) => typeof v === 'boolean';
const sendError = (res, status, message) => res.status(status).json({ error: message });

// GET collection (có thể lọc theo completed)
app.get('/api/v1/tasks', (req, res) => {
  const { completed } = req.query;
  if (completed !== undefined && !['true', 'false'].includes(completed))
    return sendError(res, 400, 'completed phải là true hoặc false');
  const result = completed === undefined
    ? tasks : tasks.filter(t => t.completed === (completed === 'true'));
  res.json({ data: result, total: result.length });
});

// GET một resource
app.get('/api/v1/tasks/:id', (req, res) => {
  const task = byId(req.params.id);
  if (!task) return sendError(res, 404, 'Không tìm thấy task');
  res.json(task);
});

// POST tạo mới
app.post('/api/v1/tasks', (req, res) => {
  const { title, completed = false } = req.body ?? {};
  if (!validTitle(title) || !validCompleted(completed))
    return sendError(res, 400, 'title và completed không hợp lệ');
  const task = { id: nextId++, title: title.trim(), completed };
  tasks.push(task);
  res.status(201).location(`/api/v1/tasks/${task.id}`).json(task);
});

// PUT thay thế đầy đủ nội dung task
app.put('/api/v1/tasks/:id', (req, res) => {
  const task = byId(req.params.id);
  if (!task) return sendError(res, 404, 'Không tìm thấy task');
  const { title, completed } = req.body ?? {};
  if (!validTitle(title) || !validCompleted(completed))
    return sendError(res, 400, 'PUT cần cả title và completed hợp lệ');
  task.title = title.trim();
  task.completed = completed;
  res.json(task);
});

// PATCH chỉ sửa trường được gửi đến
app.patch('/api/v1/tasks/:id', (req, res) => {
  const task = byId(req.params.id);
  if (!task) return sendError(res, 404, 'Không tìm thấy task');
  const patch = req.body;
  if (!patch || typeof patch !== 'object' || Array.isArray(patch))
    return sendError(res, 400, 'Body phải là JSON object');
  const keys = Object.keys(patch);
  if (!keys.length || keys.some(k => !['title', 'completed'].includes(k)))
    return sendError(res, 400, 'Chỉ cho phép title hoặc completed');
  if ('title' in patch && !validTitle(patch.title))
    return sendError(res, 400, 'title không hợp lệ');
  if ('completed' in patch && !validCompleted(patch.completed))
    return sendError(res, 400, 'completed phải là boolean');
  if ('title' in patch) task.title = patch.title.trim();
  if ('completed' in patch) task.completed = patch.completed;
  res.json(task);
});

// DELETE xóa resource
app.delete('/api/v1/tasks/:id', (req, res) => {
  const index = tasks.findIndex(t => t.id === Number(req.params.id));
  if (index < 0) return sendError(res, 404, 'Không tìm thấy task');
  tasks.splice(index, 1);
  res.status(204).end();
});

// JSON sai cú pháp → trả 400 thay vì lỗi máy chủ
app.use((err, req, res, next) => {
  if (err instanceof SyntaxError && 'body' in err)
    return sendError(res, 400, 'JSON không hợp lệ');
  next(err);
});

app.listen(3000, () => console.log('API: http://localhost:3000'));

Bước 3 · Chạy server và kiểm tra

Truy cập http://localhost:3000/api/v1/tasks bằng trình duyệt để xem JSON. Sau đó dùng terminal và curl ở phần tiếp theo để thử tạo/sửa/xóa. Các endpoint được triển khai trong server:

Gọi REST API bằng curl và fetch

Hai cách thực hành phổ biến: dùng terminal để kiểm thử, dùng JavaScript để tích hợp giao diện.

Với curl

TERMINAL · CURL
# 1. Lấy danh sách
curl -i http://localhost:3000/api/v1/tasks

# 2. Tạo một task
curl -i -X POST http://localhost:3000/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Học REST API","completed":false}'

# 3. Lấy task có id = 1
curl -i http://localhost:3000/api/v1/tasks/1

# 4. Cập nhật một trường
curl -i -X PATCH http://localhost:3000/api/v1/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"completed":true}'

# 5. Xóa task
curl -i -X DELETE http://localhost:3000/api/v1/tasks/1

-i in cả HTTP headers; -X chỉ method; -H thêm header; -d gửi request body. Lệnh giả định server đang chạy trên localhost:3000.

Với JavaScript fetch()

JAVASCRIPT · FETCH API
// Ví dụ chạy trong trang web cùng origin với API,
// hoặc ở origin được máy chủ cho phép qua CORS.
async function getTasks() {
  const response = await fetch('http://localhost:3000/api/v1/tasks', {
    headers: { Accept: 'application/json' }
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

async function createTask(title) {
  const response = await fetch('http://localhost:3000/api/v1/tasks', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ title, completed: false })
  });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || `HTTP ${response.status}`);
  }
  return response.json(); // POST thành công: 201 + JSON
}

// Lưu ý: với DELETE trả 204, không gọi response.json().
Hai điểm dễ sai(1) fetch() thường không tự throw khi API trả 4xx/5xx: hãy kiểm tra response.ok. (2) Với 204 No Content, không được gọi response.json() vì body rỗng.

CORS khi mở HTML trực tiếp: nếu một trang khác origin gọi localhost:3000, trình duyệt có thể chặn đọc response do CORS. Ví dụ Express chưa cấu hình CORS. Hãy thử bằng curl trước, hoặc triển khai frontend cùng origin, hoặc cấu hình CORS một cách giới hạn trên server khi thực sự cần.

Đi xa hơn: cache, concurrency, tài liệu và độ tin cậy

Những chủ đề xuất hiện ngay khi API có nhiều người dùng hoặc cần chạy production.

Cache-Control và ETag

HTTP hỗ trợ cache bằng Cache-Control, ETag, If-None-Match. Client có thể kiểm tra resource đã thay đổi chưa; nếu chưa, server trả 304 Not Modified thay vì gửi lại toàn bộ body.

HTTP · CONDITIONAL REQUEST
GET /api/v1/tasks/1
If-None-Match: "task-1-v7"

# Nếu resource chưa đổi:
HTTP/1.1 304 Not Modified
ETag: "task-1-v7"
# 304 không có response body

Tránh ghi đè cập nhật đồng thời

Nếu hai client cùng đọc một task rồi sửa, client cập nhật sau có thể ghi đè thay đổi của client trước. Một cách xử lý là optimistic concurrency dùng ETag và If-Match; server có thể phản hồi 412 Precondition Failed khi điều kiện không thỏa.

Retry và Idempotency-Key

Lỗi mạng có thể làm client không biết POST tạo đơn hàng đã thành công chưa. Không nên retry tạo đơn hàng một cách mù quáng. Một số API hỗ trợ Idempotency-Key nhằm nhận diện yêu cầu lặp, nhưng phải tuân theo hợp đồng của API đó (phạm vi, thời gian lưu và cách xử lý request).

OpenAPI: viết hợp đồng trước/sau khi code

OpenAPI giúp mô tả endpoints, schema, status và authentication theo định dạng máy đọc được; có thể hỗ trợ tạo tài liệu tương tác và sinh SDK.

OPENAPI YAML · VÍ DỤ TỐI GIẢN
openapi: 3.0.3
info:
  title: Task API
  version: 1.0.0
paths:
  /api/v1/tasks:
    get:
      summary: Lấy danh sách công việc
      responses:
        '200':
          description: Danh sách công việc

Production checklist

  • Authentication & authorization.
  • Schema validation.
  • Database & migration.
  • Log có request ID.
  • Metrics, tracing, alert.
  • Timeout và retry có kiểm soát.
  • Rate limiting.
  • API contract & versioning.
  • Unit/integration tests.
  • Không lộ dữ liệu nhạy cảm.
