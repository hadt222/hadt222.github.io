01 / Foundation

NGINX là gì? Dùng để làm gì?

NGINX (đọc là “engine-x”) là web server và reverse proxy hiệu năng cao; nó còn có thể cân bằng tải, cache nội dung và xử lý proxy TCP/UDP. Phiên bản NGINX Open Source đủ cho rất nhiều bài toán phổ biến.

01 · WEB SERVER

Phục vụ file tĩnh

Trả HTML, CSS, JavaScript, hình ảnh trực tiếp từ ổ đĩa.

02 · REVERSE PROXY

Đứng trước ứng dụng

Nhận HTTP(S) công khai rồi chuyển tới Node.js, Python, Go, Java…

03 · LOAD BALANCER

Chia lưu lượng

Phân phối request tới nhiều backend để tăng khả năng phục vụ.

🌐 Trình duyệtClient→⬢ NGINXPort 80 / 443→⚙ Ứng dụngPort 3000 / 8000

NGINX có master process quản lý cấu hình và worker processes xử lý kết nối theo mô hình event-driven. Nó thường đứng ở edge (điểm vào mạng) để tập trung TLS, routing, log và một phần chính sách bảo mật.

Phân biệt quan trọng

NGINX không tự biến mã nguồn Node.js/Python thành ứng dụng chạy được. Bạn vẫn cần chạy backend bằng runtime/process manager/container riêng; NGINX chỉ phục vụ file hoặc chuyển tiếp request tới backend.

03 / Installation

Cài đặt NGINX

Cách A — Ubuntu / Debian (gói của distro)

Đây là đường đi đơn giản nhất cho người mới. Gói NGINX từ repository mặc định có thể khác phiên bản gói do nginx.org phát hành.

terminal · Ubuntu / Debian
sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx --no-pager
nginx -v
curl -I http://127.0.0.1

Nếu UFW được bật, mở 80/443. Lưu ý chỉ thay đổi firewall khi bạn hiểu chính sách hiện có và không chặn cổng SSH đang sử dụng.

terminal · chỉ khi dùng UFW
sudo ufw status
sudo ufw allow 'Nginx Full'  # HTTP 80 + HTTPS 443
sudo ufw status

Cách B — Fedora / RHEL family

terminal · RHEL / Rocky / Alma / Fedora
sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo nginx -t

Với RHEL family, SELinux và firewalld có thể ảnh hưởng đến proxy hoặc quyền đọc file. Xem mục khắc phục lỗi trước khi thay đổi chính sách SELinux.

Cách C — Docker (không cần cài NGINX trên host)

terminal · Docker
docker run -d --name nginx-hello -p 8080:80 nginx:alpine
curl -I http://localhost:8080
docker logs nginx-hello
docker rm -f nginx-hello
Chọn nguồn gói ở production

Nếu cần phiên bản NGINX upstream mới hơn, hãy dùng repository chính thức theo nginx.org/linux_packages.html thay vì trộn nhiều repository. File cấu hình và module có thể khác tùy cách cài.

05 / Syntax

Hiểu cấu trúc nginx.conf

Một directive kết thúc bằng ;; block có dấu { }. Các block được lồng theo context. Ví dụ sau là cấu trúc minh họa đầy đủ, không phải nội dung để dán vào conf.d/site.conf.

/etc/nginx/nginx.conf · cấu trúc minh họa
worker_processes auto;         # MAIN context

events {
    worker_connections 1024;   # EVENTS context
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile      on;

    # SERVER context = virtual host
    server {
        listen 80;
        server_name example.com;
        root /var/www/example.com/html;
        index index.html;

        # LOCATION context = xử lý một nhóm URL
        location / {
            try_files $uri $uri/ =404;
        }
    }
}
ContextVai tròVí dụ directive
mainĐiều khiển worker và tiến trìnhworker_processes
eventsCấu hình xử lý kết nốiworker_connections
httpThiết lập chung cho HTTPinclude, gzip, upstream
serverVirtual host theo port / hostnamelisten, server_name
locationXử lý URL cụ thểroot, try_files, proxy_pass
Lỗi cấu hình rất thường gặp

Nếu file /etc/nginx/conf.d/example.conf được include bên trong http {}, file đó thường chỉ cần server { ... }, không bọc thêm http {}. Ngược lại, map, upstream và limit_req_zone phải đặt ở context http, không đặt trong location.

07 / Hands-on lab

Lab 1 — Dựng website HTML tĩnh

Mục tiêu: truy cập http://example.com và nhìn thấy file index.html do NGINX phục vụ trực tiếp.

1
Tạo thư mục và trang HTML mẫu

Đường dẫn website là tùy chọn; ví dụ dùng /var/www/example.com/html.

terminal · tạo nội dung tĩnh
sudo mkdir -p /var/www/example.com/html
printf '%s\n' '<h1>Hello from NGINX!</h1>' | \
  sudo tee /var/www/example.com/html/index.html
sudo chmod -R a+rX /var/www/example.com/html
2
Tạo virtual host

Ví dụ giả định conf.d/*.conf đang được include trong http. Đối với Debian/Ubuntu, bạn cũng có thể dùng sites-available/sites-enabled nếu cấu hình nạp thư mục đó.

/etc/nginx/conf.d/example.com.conf · HTTP static
server {
    listen 80;
    server_name example.com www.example.com;

    root /var/www/example.com/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    access_log /var/log/nginx/example.access.log;
    error_log  /var/log/nginx/example.error.log warn;
}
3
Kiểm tra rồi nạp lại

Đảm bảo DNS trỏ về server hoặc thử với header Host trên chính máy chủ.

terminal · kiểm tra virtual host
sudo nginx -t && sudo systemctl reload nginx
curl -i -H 'Host: example.com' http://127.0.0.1/
# Khi DNS đã đúng:
curl -I http://example.com
Nếu hiện “Welcome to nginx!” thay vì trang của bạn

Có thể đang gặp default server, file cấu hình chưa được include hoặc hostname không khớp. Kiểm tra sudo nginx -T, server_name, DNS và các file mặc định đang bật. Không xóa cấu hình mặc định trên máy production khi chưa biết nó đang phục vụ gì.

08 / Routing

location, root, alias và try_files

NGINX chọn location như thế nào?

Ở mức căn bản: NGINX xét location chính xác = trước; ghi nhớ prefix dài nhất; prefix ^~ được ưu tiên hơn regex; nếu không, regex khớp đầu tiên theo thứ tự khai báo có thể thắng prefix thường. Với cấu hình lồng nhau có thêm chi tiết, nên đọc tài liệu chính thức.

Cú phápÝ nghĩaVí dụ URL
location = /healthKhớp chính xác/health
location ^~ /assets/Prefix; nếu được chọn sẽ không xét regex cạnh tranh/assets/app.js
location /api/Khớp prefix/api/users
location ~ \.php$Regex phân biệt hoa/thường/index.php
location ~* \.png$Regex không phân biệt hoa/thường/PHOTO.PNG

root khác alias

ROOT · nối cả URI

root /var/www/site;

URL /img/a.png → file /var/www/site/img/a.png.

ALIAS · thay prefix

alias /srv/media/;

Nếu location /media/, URL /media/a.png → file /srv/media/a.png.

snippet · đặt bên trong server { }
# root: đường dẫn file = root + toàn bộ URI
location /images/ {
    root /var/www/site;
    try_files $uri =404;
}

# alias: thay /downloads/ bằng /srv/public-files/
location /downloads/ {
    alias /srv/public-files/;
}

# Chỉ trả file hoặc 404
location = /robots.txt {
    try_files $uri =404;
}
Ghi nhớ dấu “/”

Với prefix location kết thúc bằng /, đường dẫn alias thường cũng nên kết thúc bằng /. try_files $uri $uri/ /index.html; rất phù hợp cho SPA; nhưng không nên dùng fallback như vậy cho mọi API hay file tĩnh cần báo 404.

09 / Reverse proxy

Lab 2 — Reverse proxy tới Node.js / Python / Go

Giả sử backend đang nghe tại 127.0.0.1:3000. Client truy cập cổng 80 (sau này là 443), NGINX chuyển request tới ứng dụng.

/etc/nginx/conf.d/app.conf · reverse proxy HTTP
server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}

Ý nghĩa các directive

DirectiveChức năng
proxy_passĐịa chỉ upstream mà NGINX sẽ chuyển request đến.
proxy_set_header Host $hostChuyển hostname tới backend.
X-Real-IPThông tin địa chỉ IP peer mà NGINX nhìn thấy.
X-Forwarded-ForChuỗi IP qua các proxy; backend phải kiểm soát proxy đáng tin.
X-Forwarded-ProtoCho backend biết scheme mà NGINX nhận được.
proxy_connect_timeoutGiới hạn thời gian thiết lập kết nối upstream.
proxy_read_timeoutThời gian chờ giữa các lần đọc từ upstream, không phải tổng thời gian request.

Bẫy dấu slash trong proxy_pass

snippet · so sánh URL khi proxy
# Request: GET /api/users?id=1
location /api/ {
    proxy_pass http://127.0.0.1:3000;
}
# Backend nhận: /api/users?id=1 (giữ nguyên prefix /api/)

location /api/ {
    proxy_pass http://127.0.0.1:3000/;
}
# Backend nhận: /users?id=1 (thay /api/ bằng /)

location /api/ {
    proxy_pass http://127.0.0.1:3000/v1/;
}
# Backend nhận: /v1/users?id=1
Đây là lỗi 404 / route sai rất hay gặp

Dấu slash ở cuối proxy_pass không chỉ là trang trí: nó quyết định cách thay phần URI khớp prefix. Khi dùng location regex hoặc rewrite phức tạp, quy tắc khác đi; tham khảo tài liệu chính thức trước khi áp dụng.

10 / Application patterns

Lab 3 — React/Vue SPA + API trên cùng domain

Dùng NGINX phục vụ bản build frontend và chuyển mọi request /api/ tới backend trên port 3000. Backend trong ví dụ được thiết kế để nhận URL còn nguyên prefix /api/.

/etc/nginx/conf.d/spa.conf · ví dụ hoàn chỉnh trên HTTP
server {
    listen 80;
    server_name app.example.com;

    root /var/www/app/dist;
    index index.html;

    # API: ưu tiên prefix này, không để regex asset bắt nhầm
    location ^~ /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # File có hash do bundler tạo, có thể cache lâu
    location ~* \.(?:js|css|png|jpg|jpeg|svg|woff2)$ {
        try_files $uri =404;
        expires 7d;
        add_header Cache-Control "public";
    }

    # SPA client-side routing: /dashboard → index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}

Hãy copy thư mục build (thường là dist/) vào /var/www/app/dist và đảm bảo user NGINX đọc được. Với asset không có hash trong tên file, nên đặt TTL ngắn hơn và cấu hình cache phù hợp với cách phát hành.

Không fallback API thành HTML

Nếu API gặp 404 mà browser nhận trang index.html, nhiều khả năng request đi vào location / thay vì proxy API. Hãy kiểm tra prefix /api/, cấu hình route và thứ tự ưu tiên location.

11 / TLS & certificates

HTTPS với Let's Encrypt và Certbot

HTTPS mã hóa kết nối giữa browser và NGINX. Bạn cần DNS công khai trỏ đúng, cổng kiểm tra ACME phù hợp (thường 80 cho HTTP challenge), quyền cấu hình NGINX và tên miền thuộc quyền kiểm soát của bạn.

Cấp chứng chỉ tự động với Certbot

Đoạn dưới minh họa Ubuntu có snapd. Nếu đã cài Certbot bằng apt/dnf trước đó, làm theo hướng dẫn chuyển đổi chính thức; tránh giữ hai bản Certbot gây xung đột lệnh.

terminal · Ubuntu + snapd, domain đã hoạt động trên HTTP
# Nếu máy chưa có snapd:
sudo apt update
sudo apt install -y snapd

# Cài Certbot theo hướng dẫn snap chính thức
sudo snap install --classic certbot
# Tạo symlink nếu /usr/local/bin/certbot chưa tồn tại:
sudo ln -s /snap/bin/certbot /usr/local/bin/certbot

# Certbot tự xin chứng chỉ và cấu hình NGINX
sudo certbot --nginx -d example.com -d www.example.com

# Kiểm tra gia hạn tự động
sudo certbot renew --dry-run

Nếu /usr/local/bin/certbot đã tồn tại, không tạo symlink chồng lên; kiểm tra command -v certbot. Certbot có thể chỉnh trực tiếp file cấu hình. Hãy sao lưu và đọc phần thay đổi trước khi áp dụng trong môi trường quan trọng.

Cấu hình HTTPS thủ công sau khi đã có chứng chỉ

/etc/nginx/conf.d/secure-app.conf · chỉ dùng khi cert đã tồn tại
# HTTP -> HTTPS
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com www.example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Đừng bật HTTPS config quá sớm

Nếu đường dẫn fullchain.pem/privkey.pem chưa có, nginx -t sẽ lỗi. Hãy để Certbot cấp cert trước hoặc dùng cơ chế challenge thích hợp. Chỉ bật HSTS khi mọi subdomain và đường dẫn phục vụ HTTPS đã được kiểm tra kỹ; HSTS có thể khiến rollback về HTTP khó hơn.

12 / Scale

Cân bằng tải với upstream

Khi có nhiều instance backend, NGINX có thể phân phối request qua upstream group. Mặc định là round-robin (theo lượt); còn có least_conn và các lựa chọn khác.

/etc/nginx/conf.d/balancer.conf · file được include trong http {}
upstream app_cluster {
    least_conn;                    # chuyển tới backend ít kết nối hơn
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003 backup;  # khi upstream chính không khả dụng
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://app_cluster;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

NGINX Open Source có các cơ chế phát hiện lỗi upstream thụ động; khả năng active health checks nâng cao phụ thuộc phiên bản/sản phẩm, ví dụ NGINX Plus. Ứng dụng nhiều instance cần quản lý session, cache, file upload và trạng thái dùng chung một cách phù hợp.

Round-robin vs least connections

Bỏ least_conn; nếu muốn round-robin. Không nên mặc định rằng phân phối sẽ đều tuyệt đối trong mọi tình huống, vì keepalive, request duration, lỗi backend và số worker đều ảnh hưởng.

13 / Real-time

Proxy WebSocket (chat, notification, realtime)

WebSocket cần HTTP upgrade handshake. Hai header Upgrade và Connection phải được truyền đúng khi NGINX làm reverse proxy.

nginx.conf / conf.d/*.conf · map ở http, location ở server
# Đặt ở context http (ngoài server)
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name ws.example.com;

    location /ws/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;  # rõ ràng, tương thích bản NGINX cũ
        proxy_set_header Host       $host;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
    }
}

proxy_read_timeout cần tương thích nhịp ping/pong của app. Các kết nối WebSocket dài có thể cần cơ chế sticky session hoặc pub/sub nếu chạy nhiều backend.

Nguồn: WebSocket proxying — nginx.org.

14 / Performance

Tối ưu cơ bản: Gzip, static cache và proxy cache

Gzip cho text asset

Đoạn này thuộc context http (có thể tách file include hợp lệ trong context đó). Không nén lại nội dung vốn đã nén như JPEG/PNG/MP4.

nginx.conf · bên trong http { }
gzip on;
gzip_vary on;
gzip_min_length 1024;
gzip_comp_level 5;
gzip_types text/plain text/css application/javascript
           application/json application/xml image/svg+xml;

Cache trình duyệt cho asset có fingerprint

snippet · bên trong server { }
location ~* \.(?:css|js|woff2|svg|png|jpg|jpeg)$ {
    try_files $uri =404;
    expires 30d;
    add_header Cache-Control "public";
}

# HTML đổi thường xuyên: không cache dài hạn
location = /index.html {
    add_header Cache-Control "no-cache";
}

Với cấu hình này, regex asset sẽ xử lý file đúng extension ở mọi path; nếu có API trùng extension, dùng prefix ^~ /api/ như ví dụ SPA để tránh bị bắt nhầm. add_header có quy tắc kế thừa theo context: khai báo header mới trong location có thể khiến header ở context cha không được kế thừa trên phiên bản/thiết lập cụ thể.

Reverse proxy cache — chỉ cho endpoint công khai

example · cần ghép vào config phù hợp, không dán ngoài context
# Đặt trong http { }
proxy_cache_path /var/cache/nginx/public
    levels=1:2 keys_zone=public_cache:10m
    max_size=1g inactive=30m use_temp_path=off;

# Đặt trong server { } đang proxy tới backend
location /public-api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_cache public_cache;
    proxy_cache_methods GET HEAD;
    proxy_cache_valid 200 5m;
    proxy_cache_bypass $http_authorization;
    proxy_no_cache $http_authorization;
    add_header X-Cache $upstream_cache_status always;
}
Không cache dữ liệu cá nhân nếu chưa thiết kế cache key/chính sách kỹ

Chỉ dùng mẫu trên cho tài nguyên thực sự public, không thay đổi theo user, cookie, session, phân quyền hay header tùy biến. Cache response có nội dung riêng tư có thể rò rỉ dữ liệu. Kiểm tra response headers (ví dụ Cache-Control, Set-Cookie) và cách sinh cache key trước khi dùng ở production.

15 / Security

Bảo mật cấu hình NGINX

NGINX giúp giảm bề mặt tấn công, nhưng không thay thế cập nhật hệ điều hành, vá ứng dụng, xác thực hay WAF. Áp dụng từng chính sách theo luồng traffic thực tế.

nginx.conf · đặt bên trong http { }
server_tokens off;                 # không hiển thị version trong header/error page
client_max_body_size 10m;         # điều chỉnh theo nhu cầu upload

# Mỗi IP trung bình 5 request/giây cho vùng login
limit_req_zone $binary_remote_addr zone=login_rate:10m rate=5r/s;
snippet · bên trong server { }
autoindex off;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

# Không public file/directory ẩn, ngoại trừ .well-known
location ~ /\.(?!well-known(?:/|$)) {
    deny all;
}

# Hạn chế request tới trang đăng nhập
location /login/ {
    limit_req zone=login_rate burst=10 nodelay;
    limit_req_status 429;
    proxy_pass http://127.0.0.1:3000;
}
TRUST PROXY

IP thực của client

Nếu đứng sau CDN/LB, cấu hình real_ip_header và set_real_ip_from chỉ cho IP proxy đáng tin. Đừng tin mọi header do client tự gửi.

HEADERS

Security headers

CSP, HSTS, frame policies cần thiết kế theo ứng dụng. Không bật bừa một giá trị khi chưa thử tài nguyên third-party, subdomain và callback OAuth.

Giới hạn tốc độ không phải chống DDoS hoàn chỉnh

limit_req hữu ích cho endpoint nhạy cảm nhưng phải tính đến proxy/CDN, NAT chung IP, khả năng burst hợp lệ và hành vi 429. Đánh giá bằng traffic và log thật trước khi siết chặt.

16 / Observability

Đọc access log, error log và debug

terminal · nhanh nhất để tìm lỗi
sudo tail -n 100 /var/log/nginx/error.log
sudo tail -f /var/log/nginx/access.log
sudo journalctl -u nginx --since '30 minutes ago'

Đo thời gian upstream trong access log

Ở http, định nghĩa format rồi bật trong server. Các biến $upstream_response_time và $request_time giúp phát hiện nơi chậm.

nginx.conf · http { } rồi server { }
# Bên trong http { }
log_format timing '$remote_addr "$request" status=$status '
                  'request_time=$request_time '
                  'upstream_time=$upstream_response_time '
                  'upstream_addr=$upstream_addr';

# Bên trong server { }
access_log /var/log/nginx/app-timing.log timing;

Trong môi trường container, log thường được đưa ra stdout/stderr để hệ thống thu thập. Tránh ghi cookie, access token, thông tin nhạy cảm hoặc payload cá nhân trực tiếp vào log.

Docker Compose: frontend proxy đến backend

Trong mạng Docker Compose, NGINX gọi backend qua service name api:3000, không phải localhost:3000 (vì localhost trong container là chính container đó). Mẫu sau giả định có thư mục backend/ chứa Dockerfile cho API nghe port 3000.

compose.yaml · ví dụ minh họa dự án có backend/Dockerfile
services:
  api:
    build: ./backend
    expose:
      - "3000"

  nginx:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - api
nginx/default.conf · trong container
server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://api:3000;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
terminal · các lệnh Compose
docker compose up -d --build
docker compose ps
docker compose logs -f nginx
docker compose exec nginx nginx -t
docker compose down
Lưu ý triển khai container

depends_on điều khiển thứ tự khởi động cơ bản nhưng không mặc định chờ app thật sự healthy. Khi backend restart, chiến lược DNS/re-resolve của NGINX phụ thuộc cách cấu hình upstream và phiên bản; cần test tình huống thay container trước khi production. Mẫu Compose này không tự cấp HTTPS.

19 / Reference design

Blueprint — Static SPA + API + HTTPS

Đây là mẫu để tham khảo sau khi đã có chứng chỉ tại /etc/letsencrypt/live/app.example.com/, frontend được build vào /var/www/app/dist, backend chạy tại 127.0.0.1:3000 và file được include trong http {}.

/etc/nginx/conf.d/app.example.com.conf · TLS + SPA + /api
server {
    listen 80;
    server_name app.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    root /var/www/app/dist;
    index index.html;
    client_max_body_size 10m;
    server_tokens off;

    add_header X-Content-Type-Options "nosniff" always;

    # Backend giữ nguyên prefix /api/
    location ^~ /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }

    # Chỉ cache dài nếu asset có fingerprint/hash version
    location ~* \.(?:js|css|woff2|png|svg)$ {
        try_files $uri =404;
        expires 7d;
        add_header Cache-Control "public";
        add_header X-Content-Type-Options "nosniff" always;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

# Kiểm tra: sudo nginx -t && sudo systemctl reload nginx
Phạm vi blueprint

Đây không phải cấu hình production “chuẩn cho mọi hệ thống”: bạn cần điều chỉnh cache headers, TLS, CSP, rate limiting, log, upstream timeout và trusted proxy theo app/CDN/phiên bản đang chạy. Nếu đã dùng certbot --nginx, không tạo thêm một virtual host HTTPS trùng tên mà không hợp nhất cấu hình.

Bonus / FAQ

Câu hỏi hay gặp

NGINX khác Apache ở đâu?

Cả hai đều là web server. NGINX nổi bật ở mô hình event-driven và rất phổ biến với reverse proxy/static content; Apache có hệ sinh thái module và cách cấu hình linh hoạt. Chọn theo đặc thù ứng dụng và năng lực vận hành.

Có cần NGINX nếu backend đã chạy HTTP được rồi?

Không bắt buộc cho mọi ứng dụng nhỏ, nhưng NGINX hữu ích khi muốn đặt một điểm vào HTTPS, phục vụ tài nguyên tĩnh, định tuyến nhiều app, thiết lập cache/rate limit và chuẩn hóa access log.

sites-enabled và conf.d khác nhau thế nào?

conf.d thường chứa file *.conf được include trực tiếp; sites-enabled thường gồm symlink tới file trong sites-available trên các gói Debian/Ubuntu. Hãy kiểm tra nginx -T vì distro khác nhau có default khác nhau.

Vì sao proxy_pass http://localhost:3000 trong Docker lỗi?

Bởi localhost trong container NGINX không trỏ tới container API. Trong Compose, dùng tên dịch vụ backend như http://api:3000 và bảo đảm các service nằm trên cùng mạng.

Có nên chỉnh worker_processes và worker_connections để tối ưu?

Có thể, nhưng đừng tăng tùy tiện. worker_processes auto; là điểm khởi đầu hợp lý; hiệu năng phụ thuộc CPU, file descriptors, kernel limits, TLS, upstream và lượng traffic. Nên đo tải trước và sau khi thay đổi.

Có thể sử dụng file HTML này không có internet?

Có. Toàn bộ CSS, JavaScript và nội dung của tutorial nằm trong một file. Chỉ những link tài liệu tham khảo đi ra ngoài mới cần kết nối mạng.
