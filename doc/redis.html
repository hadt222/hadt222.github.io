01 · NỀN TẢNG

Redis là gì?

Hiểu đúng vai trò của Redis trước khi gõ lệnh.

Redis là kho dữ liệu lưu chủ yếu trong RAM (in-memory data store), thao tác theo mô hình key → value và hỗ trợ nhiều cấu trúc dữ liệu. Redis thường được dùng làm cache, session store, bộ đếm, bảng xếp hạng, hàng đợi và hệ thống truyền thông điệp. Redis cũng có cơ chế ghi dữ liệu xuống đĩa, nhưng không nên mặc định xem đó là bản thay thế trực tiếp cho database giao dịch chính.

⚡

Truy cập nhanh

Thao tác trên RAM giảm độ trễ, phù hợp đường truy cập nóng và request có tần suất cao.

🧩

Giàu cấu trúc

String, Hash, List, Set, Sorted Set, Stream cùng các kiểu dữ liệu mở rộng.

🛡️

Linh hoạt

TTL, replication, persistence, ACL, TLS và cluster cho nhiều yêu cầu vận hành.

Redis nằm ở đâu trong hệ thống?

👤ClientWeb / Mobile
→
⌘Backend APINode / Python / Go
↗ Cache hit↘ Cache miss
◆ RedisFast access
▤ DatabaseSource of truth

Luồng cache-aside: API thử GET từ Redis; nếu chưa có thì đọc cơ sở dữ liệu, ghi kết quả vào Redis với TTL, rồi trả dữ liệu cho client. Redis tăng tốc đường đọc, còn database chính chịu trách nhiệm dữ liệu bền vững.

✦
Điểm cần nhớ
Redis không đồng nghĩa với cache. Nó là kho cấu trúc dữ liệu đa dụng; tuy nhiên mọi dữ liệu quan trọng vẫn cần chiến lược độ bền, backup và khôi phục cụ thể.
02 · KHỞI ĐỘNG

Cài đặt & chạy Redis

Ưu tiên Docker để thao tác giống nhau trên macOS, Linux và Windows.

Cách 1 — Docker (khuyến nghị cho bài học)

TerminalBASH
# Tạo Redis cho máy local; chỉ bind về loopback của máy chủ
# Volume lưu dữ liệu Redis trên máy qua Docker

docker run -d --name redis-lab \
  -p 127.0.0.1:6379:6379 \
  -v redis-lab-data:/data \
  redis:8 redis-server --appendonly yes

# Mở redis-cli bên trong container
docker exec -it redis-lab redis-cli

# Kiểm tra kết nối
PING
# PONG
!
Lưu ý cổng 6379
Chỉ expose Redis cho localhost khi học. Trong production, không công khai Redis trực tiếp ra Internet. Docker volume giữ file dữ liệu khi container bị xóa, nhưng không thay thế backup.

Cách 2 — Các hệ điều hành khác

Hệ điều hànhGợi ý
macOSDùng Homebrew: brew install redis và chạy redis-server trong terminal.
LinuxDùng gói Redis từ kho chính thức phù hợp distro hoặc Docker.
WindowsChạy Redis bằng Docker Desktop hoặc môi trường Linux/WSL; hướng dẫn chính thức ưu tiên Docker.

Kiểm tra và dọn dẹp

TerminalBASH
docker exec redis-lab redis-cli PING
# PONG

docker logs redis-lab

docker stop redis-lab
# Chạy lại khi cần:
docker start redis-lab
# Xóa container khi xong (volume vẫn còn):
docker rm -f redis-lab

Quy ước: những khối mã mang nhãn redis-cli được nhập trong Redis CLI, không chạy trực tiếp ở shell hệ điều hành. Nếu bạn chưa ở trong CLI, dùng docker exec redis-lab redis-cli <lệnh>.

03 · THỰC HÀNH

Lệnh Redis CLI đầu tiên

Tạo, đọc, sửa, xóa một key và hiểu phản hồi của Redis.

redis-cliREDIS
PING                          # kiểm tra server
SET greeting "Xin chao Redis" # ghi chuỗi
GET greeting                  # đọc chuỗi
EXISTS greeting               # key có tồn tại? (1 hoặc 0)
TYPE greeting                 # kiểu dữ liệu: string
DEL greeting                  # xóa key
GET greeting                  # (nil), key không tồn tại
DBSIZE                        # số key của DB hiện tại
i
Cú pháp của ví dụ
Chữ sau dấu # là chú thích giải thích cho người đọc. Khi thực hành, hãy nhập phần lệnh trước dấu # để tránh khác biệt xử lý chú thích giữa các môi trường.

Đặt tên key dễ quản lý

Gợi ý key namingREDIS
app:dev:user:42
app:dev:session:abc123
app:dev:cache:product:9001
app:dev:rate:login:203.0.113.5
  • Tên key thường chia theo ứng dụng : môi trường : tài nguyên : ID.
  • Tránh key quá dài, chứa dữ liệu bí mật hay không có prefix rõ ràng.
  • Các key liên quan nên có quy ước TTL nhất quán.
  • Trong Redis Cluster, cart:{42}:items và cart:{42}:total có cùng hash tag {42}, nên có thể nằm cùng hash slot.
04 · CỐT LÕI

Các kiểu dữ liệu quan trọng

Chọn đúng cấu trúc dữ liệu quan trọng hơn việc cố lưu mọi thứ dưới dạng JSON.

KiểuĐặc điểmVí dụ dùng
StringChuỗi, số, byte; hỗ trợ tăng/giảm nguyên tửCache kết quả, token, counter
HashMap field → valueHồ sơ người dùng, thuộc tính
ListDanh sách có thứ tự, thao tác ở hai đầuQueue đơn giản, lịch sử gần đây

String — lưu giá trị và counter

redis-cliREDIS

GET profile:42:name
MSET site:name "Demo" site:locale "vi"
MGET site:name site:locale

INCR views:post:9

Lệnh INCR là thao tác nguyên tử trên Redis; rất hữu ích với bộ đếm. Giá trị phải có thể diễn giải là số nguyên.

HMGET user:42 name plan

HINCRBY user:42 login_count 1

redis-cliREDIS

List thích hợp cho danh sách nhỏ hoặc queue đơn giản. Với hàng đợi có xác nhận, phục hồi và nhiều worker, cân nhắc Redis Streams.

Set — không trùng phần tử

redis-cliREDIS
SADD post:9:likes "user-1" "user-2" "user-1"
SCARD post:9:likes
SISMEMBER post:9:likes "user-1"
SMEMBERS post:9:likes
SREM post:9:likes "user-2"

Sorted Set — bảng xếp hạng

redis-cliREDIS
ZADD leaderboard 120 "alice" 95 "bob" 170 "charlie"
ZINCRBY leaderboard 40 "bob"

✦
Mẹo chọn cấu trúc
Đếm lượt xem → String + INCR. Hồ sơ → Hash. Likes duy nhất → Set. Leaderboard → Sorted Set. Sự kiện cần xử lý lại → Stream.
05 · CƠ CHẾ

TTL, hết hạn & xóa key

TTL là nền tảng của caching, session và kiểm soát dữ liệu tạm.

redis-cliREDIS
SET otp:user:42 "829401" EX 120
TTL otp:user:42         # số giây còn lại
PTTL otp:user:42        # số mili giây còn lại
EXPIRE otp:user:42 300 # cập nhật TTL
PERSIST otp:user:42    # bỏ thời gian hết hạn
DEL otp:user:42        # xóa ngay
UNLINK large:key       # tách phần lớn chi phí giải phóng bộ nhớ khỏi luồng xử lý
Giá trị TTLÝ nghĩa
>= 0Số giây / mili giây còn lại
-1Key còn nhưng không có hạn
-2Key không tồn tại

Cú pháp SET key value EX seconds ghi dữ liệu và đặt hạn trong cùng một lệnh. Cách này tốt hơn việc gọi SET rồi EXPIRE tách rời nếu bạn cần đảm bảo TTL khi có lỗi giữa hai lệnh.

!
Cẩn thận với SET
SET thông thường có thể làm mất TTL đang tồn tại của key; dùng KEEPTTL khi bạn có chủ đích giữ thời gian hết hạn.

07 · PATTERN

Caching thực tế với Redis

Hiểu cache-aside, invalidation và các lỗi phổ biến khi đưa cache vào production.

Cache-aside (lazy loading)

01API đọc GET cache:product:9
02Cache hit → trả ngay
03Cache miss → query database
04SET ... EX 60 rồi trả kết quả
05Khi cập nhật DB → xóa / cập nhật key cache liên quan
redis-cliREDIS
GET cache:product:9
# Nếu nil: đọc database từ backend rồi ghi:
SET cache:product:9 '{"id":9,"name":"Ban phim"}' EX 60
# Khi sản phẩm cập nhật:
DEL cache:product:9

5 vấn đề cần biết

  • Stale cache: DB cập nhật nhưng cache cũ. Thiết kế invalidation, event-driven updates hoặc TTL thích hợp.
  • Cache penetration: truy vấn ID không tồn tại lặp lại. Cân nhắc cache negative result TTL ngắn.
  • Cache stampede: nhiều request cùng miss khi key nóng hết hạn. Dùng TTL jitter, single-flight, refresh trước hạn hoặc lock khi cần.
  • Hot key: một key nhận quá nhiều lượt đọc. Theo dõi và cân nhắc kiến trúc phân tải, local cache có kiểm soát.
  • Eviction: key có thể biến mất khi thiếu RAM. Ứng dụng phải luôn xử lý cache miss đúng cách.
✦
Nguyên tắc
Cache là lớp tối ưu có thể mất hoặc hết hạn bất cứ lúc nào; không được để tính đúng đắn nghiệp vụ phụ thuộc hoàn toàn vào cache.
08 · CODE

Kết nối Redis với Node.js

Một ví dụ cache-aside đơn giản có thể áp dụng vào API thật.

Cài package redis (node-redis). Ví dụ dưới đây dùng Node.js với ESM ("type": "module" trong package.json), Redis đã chạy tại localhost:6379.

TerminalBASH
mkdir redis-demo && cd redis-demo
npm init -y
npm pkg set type=module
npm install redis
# Tạo file app.js bằng nội dung bên dưới
node app.js
app.jsJS
import { createClient } from 'redis';

const redis = createClient({
  url: process.env.REDIS_URL ?? 'redis://127.0.0.1:6379'
});
redis.on('error', (err) => console.error('Redis error:', err));

// Hàm giả lập DB chính để minh họa.
async function loadProductFromDB(id) {
  return { id, name: 'Mechanical keyboard', price: 1200000 };
}

async function getProduct(id) {
  const key = `demo:product:${id}`;
  try {
    const cached = await redis.get(key);
    if (cached !== null) {
      console.log('CACHE HIT');
      return JSON.parse(cached);
    }
  } catch (err) {
    console.error('Cache read failed:', err.message);
  }

  const product = await loadProductFromDB(id);
  try {
    await redis.set(key, JSON.stringify(product), { EX: 60 });
  } catch (err) {
    console.error('Cache write failed:', err.message);
  }
  return product;
}

try {
  await redis.connect();
  console.log(await getProduct(42)); // DB → cache
  console.log(await getProduct(42)); // cache hit
} finally {
  if (redis.isOpen) await redis.close();
}
✦
Production checklist
Thiết lập timeout / retry phù hợp, giới hạn số lần kết nối lại, log và metric, graceful shutdown và cơ chế fallback khi Redis lỗi. Cache không được làm sập chức năng chính nếu nghiệp vụ cho phép.
09 · PATTERN

Bộ đếm & rate limiting

Giới hạn số request trong một khoảng thời gian.

Ý tưởng fixed window: mỗi client có một key theo cửa sổ thời gian; mỗi request tăng counter và so với ngưỡng. Ví dụ dưới đây dùng Lua để INCR + đặt EXPIRE cho key mới trong một thao tác nguyên tử.

rate-limit.luaLUA
-- KEYS[1]: rate:login:<client>:<window>
-- ARGV[1]: thời gian cửa sổ (giây)
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1]))
end
return count
redis-cliREDIS
# Ví dụ: 60 giây, sử dụng một key cho một cửa sổ
EVAL "local n=redis.call('INCR',KEYS[1]); if n==1 then redis.call('EXPIRE',KEYS[1],tonumber(ARGV[1])) end; return n" 1 rate:login:client-42:window-1 60
# Nếu kết quả > 5 thì API có thể trả HTTP 429
!
Lưu ý kỹ thuật
Mẫu này là fixed-window minh họa; key cần chứa định danh cửa sổ thời gian thực sự. Nó có thể cho phép dồn request ở ranh giới hai cửa sổ. Muốn hạn chế burst tốt hơn, dùng sliding window hoặc token bucket. Không dùng IP thô nếu có yêu cầu bảo vệ dữ liệu cá nhân.
10 · MESSAGING

Pub/Sub và Redis Streams

Hai công cụ tưởng giống nhau nhưng khác rõ về độ bền và cách đọc sự kiện.

Tiêu chíPub/SubStreams
Lưu thông điệpKhông có log replay mặc địnhCó log sự kiện lưu trữ
Nếu consumer offlineCó thể mất thông điệpCó thể đọc lại dữ liệu còn lưu
Xác nhận xử lýKhông có ACK built-inConsumer group + XACK
Điển hìnhNotification thời gian thựcJob / event processing

Pub/Sub — gửi tức thời

redis-cliREDIS
# Terminal A: đăng ký kênh
SUBSCRIBE news

# Terminal B: đăng ở cửa sổ CLI khác
PUBLISH news "Hello subscribers"

Pub/Sub dùng delivery kiểu at-most-once. Subscriber offline có thể mất tin. Đừng dùng Pub/Sub làm queue bền vững.

Streams — có ID, consumer group và ACK

redis-cliREDIS
# Producer: ghi sự kiện vào Stream
XADD orders * order_id 101 status paid
XADD orders * order_id 102 status paid
XRANGE orders - +

# Tạo consumer group, đọc tất cả entry hiện có từ đầu
XGROUP CREATE orders workers 0 MKSTREAM

# Worker A lấy sự kiện mới chưa phát trong group
XREADGROUP GROUP workers worker-a COUNT 10 STREAMS orders >

# Sau khi xử lý thành công, dùng ID thực nhận được
# Ví dụ minh họa; thay <entry-id> bằng ID thật:
XACK orders workers <entry-id>
✦
Streams không tự đảm bảo xử lý đúng một lần
Thiết kế handler idempotent, theo dõi pending entries (XPENDING) và dùng cơ chế claim/retry khi worker chết. Consumer group thường có semantics at-least-once khi được vận hành đúng.
11 · TÍNH ĐÚNG

Transaction, pipeline & Lua

Phân biệt tối ưu lượt mạng với thao tác nguyên tử.

MULTI / EXEC — nhóm lệnh

redis-cliREDIS
MULTI
INCR stock:sold
INCR revenue:events
EXEC

Trong Redis, các lệnh trong transaction được thực thi tuần tự, không bị lệnh client khác chen vào giữa. Khác transaction trong database quan hệ, Redis không rollback các lệnh đã chạy khi một lệnh trong EXEC lỗi runtime.

WATCH — optimistic locking

redis-cliREDIS
WATCH inventory:9
GET inventory:9
# Ứng dụng tính toán giá trị mới, ví dụ 4 → 3
MULTI
SET inventory:9 3
EXEC
# EXEC trả nil nếu key bị thay đổi trước khi EXEC

WATCH chỉ minh họa logic compare-and-set; ứng dụng cần retry và kiểm tra số lượng không âm. Một thao tác nguyên tử bằng Lua/function thường phù hợp hơn cho logic nhiều bước.

Pipeline — giảm round-trip

Pipeline gửi nhiều lệnh qua ít lượt mạng hơn để tăng throughput. Pipeline không tự trở thành transaction. Tách biệt yêu cầu tốc độ và yêu cầu atomicity.

12 · DỮ LIỆU

Persistence: RDB vs AOF

Dữ liệu nằm trong RAM nhưng có thể được ghi xuống đĩa để phục hồi.

RDBAOF
Cách lưuSnapshot theo thời điểmGhi lại các thao tác thay đổi
Ưu điểmGọn, hữu ích cho backup/restartKhả năng giảm mất dữ liệu giữa snapshot
Đánh đổiCó thể mất dữ liệu từ snapshot cuốiTăng I/O, file có thể lớn
Gợi ýBackup định kỳappendfsync everysec thường là điểm cân bằng
persistence.conf — ví dụ minh họaCONF
# Ví dụ cấu hình trong redis.conf
appendonly yes
appendfsync everysec
save 3600 1

# Kiểm tra trạng thái
# Chạy trong redis-cli:
INFO persistence
BGSAVE

Ở chế độ appendfsync everysec, thường có rủi ro mất một khoảng ghi gần nhất khi máy gặp sự cố. Không có cấu hình nào thay thế được quy trình backup và thử restore.

!
Tránh chỉnh config production thiếu kế hoạch
Sao lưu dữ liệu và xác nhận cách Redis được khởi chạy trước khi bật/tắt AOF hoặc RDB trên một instance đang có dữ liệu. Đừng sao chép đoạn cấu hình minh họa này trực tiếp lên môi trường quan trọng.
13 · TRIỂN KHAI

Replication, Sentinel & Cluster

Chọn mô hình khi một Redis instance không còn đủ.

↗

Replication

Primary → replica: tăng khả năng đọc, dự phòng, nhưng replication bất đồng bộ có thể có độ trễ.

◉

Sentinel

Giám sát và tự động failover cho kiến trúc Redis không sharding.

▦

Cluster

Chia dữ liệu ra nhiều primary theo 16.384 hash slots và hỗ trợ failover.

Sentinel không chia dữ liệu. Redis Cluster thì có sharding; nhiều thao tác đa key chỉ chạy được khi key ở cùng hash slot, do đó cần key naming / hash tag hợp lý.

High availability không đồng nghĩa zero data loss
Replication bất đồng bộ cùng failover có thể gây mất một số ghi chưa sao chép. Thiết kế theo RPO/RTO thực tế, backup và test khôi phục.
14 · VẬN HÀNH

RAM & eviction policy

Đừng để cache tăng vô hạn mà không có dự trù dung lượng.

redis-cliREDIS
# Chỉ minh họa cho Redis dùng riêng làm cache:
CONFIG SET maxmemory 256mb
CONFIG SET maxmemory-policy allkeys-lru

# Giám sát
INFO memory
INFO stats
MEMORY USAGE demo:product:42
PolicyÝ nghĩa
noevictionKhông evict theo maxmemory; lệnh ghi cần thêm RAM có thể thất bại khi chạm giới hạn
allkeys-lruLoại key ít truy cập gần đây (LRU xấp xỉ)
allkeys-lfuLoại key ít được truy cập thường xuyên (LFU xấp xỉ)
volatile-lruChỉ chọn key có TTL theo LRU
volatile-ttlƯu tiên key có TTL còn lại thấp

Chỉ đặt allkeys-* khi bạn chấp nhận mọi key có thể bị loại bỏ. Nếu Redis chứa session hay thông tin quan trọng, hãy cân nhắc tách instance/cache pool và chính sách phù hợp.

!
maxmemory ≠ toàn bộ bộ nhớ tiến trình
Vẫn cần chừa headroom cho overhead, replication buffers, fork/copy-on-write, fragmentation và hệ điều hành. Đừng cấu hình 100% RAM vật lý.
15 · PRODUCTION

Bảo mật Redis

Quy tắc tối thiểu trước khi dùng Redis ngoài máy local.

  1. Không mở Redis ra Internet. Dùng private network, firewall, security group và bind phù hợp.
  2. Phân quyền bằng ACL. Tạo account theo ứng dụng với danh sách lệnh và key pattern tối thiểu.
  3. Mã hóa kết nối. Dùng TLS khi dữ liệu đi qua mạng không tin cậy.
  4. Bảo vệ secrets. Đặt thông tin xác thực qua secret manager / env, không hardcode trong Git.
  5. Giám sát và backup. Theo dõi authentication errors, số kết nối bất thường, backup/restore và cập nhật phiên bản.
redis-cliREDIS
# Ví dụ ACL minh họa: chỉ thao tác GET/SET/DEL
# trên key có prefix cache:app:*; dùng mật khẩu bí mật mạnh.
ACL SETUSER cache_app on >REPLACE_WITH_STRONG_SECRET ~cache:app:* +GET +SET +DEL +PING

# Kiểm tra tài khoản (không in mật khẩu)
ACL GETUSER cache_app
!
Không dùng mật khẩu ví dụ
Đoạn ACL trên chỉ mang tính minh họa trong môi trường test. Quyền thực tế phụ thuộc vào command app dùng (TTL, hash, multi-key,...). Ưu tiên quản lý ACL bằng config, secret và quy trình vận hành thay vì nhập mật khẩu vào shell history.

17 · DEBUG

Các lỗi thường gặp

Tra nhanh nguyên nhân và hướng xử lý.

WRONGTYPE — thao tác sai kiểu dữ liệu+

Ví dụ gọi HGET trên key String. Chạy TYPE key, kiểm tra namespace và dữ liệu trước khi dùng lệnh.

NOAUTH / WRONGPASS — lỗi quyền truy cập+

Kiểm tra URI, ACL username/password, TLS, secret và key pattern được cấp quyền. Không in secret vào log.

OOM command not allowed+

Đọc INFO memory, CONFIG GET maxmemory và policy. Cân nhắc tăng dung lượng hoặc thay đổi chính sách theo mục đích cache/dữ liệu, không tự ý xóa key quan trọng.

Connection refused / timeout+

Kiểm tra Redis đang chạy, hostname/port, Docker network, firewall, TLS, timeout và mức tải. Trên Docker, localhost trong container khác là container đó, không phải host Redis.

Cache trả dữ liệu cũ+

Kiểm tra TTL, đường cập nhật DB, invalidation và multi-region. Gắn version vào cache key hoặc xóa key sau khi cập nhật DB thành công.
